# Rust 网络代理内核统一错误代码体系设计、实现与审查

约定等级：**MUST（强制执行）**。作者：可莉唯一的狗。

本规范适用于 Rust 网络代理内核全部模块，属于实际代码开发、审查及交付约束，不是仅供参考的设计建议。修改前必须检查当前项目、复用既有架构；任何未完成的验收不得通过推测、多个 AI 相互引用或测试绿灯宣称完成。此文登记用户确认的规范，不表示当前实现已经满足全部要求。

## 第一章：总体目标

所有对外公开错误必须有唯一、稳定、强类型、可扩展的代码。代码用于机器识别，描述用于辅助诊断，上下文用于定位，处理后果由业务规范决定，四者不得混为一谈。内核定义协议、含义、格式及兼容性，不依赖读取方。错误不得静默吞没、转成成功、默认放行、绕过认证/授权/资源限制或改变原规则语义。内核 Documentation 必须有完整《错误代码查询表.md》及自动一致性检查。必须完成 L1、L2、L3、L4 审查。

## 第二章：修改前全面审查

先确认真实内核 crate/Workspace 根目录，再检查 Error、Result、错误枚举/结构体、创建与传播、From/Into、map_err、序列化、API/实际存在的 IPC、日志、诊断、错误库及默认值/成功转换路径。必须覆盖配置、YAML/JSON、验证、规则生成/编译/匹配/覆盖裁剪、DNS、TCP/UDP、代理连接转发、Debug Overlay、预算/分配、快照/并发、持久化/恢复、权限、生命周期及其他实际模块。

识别重复标识、不同语义混用、字符串分类、散落代码、丢失原因、忽略失败、意外 DIRECT/Continue、权限误归类、预算忽略、部分接受配置、敏感信息泄漏及处理后果违约。已有能力优先复用，禁止未经检查建立平行体系。静态扫描与人工调用链核验分别记录。

## 第三章：代码命名与真实语义

代码使用显式分配的固定整数，Rust 变体名称只用于代码可读性。每个代码只能来自真实源码中的错误、已确认规范或已确认需区分的失败。不得把规范示例当成已实现功能。

代码全局唯一，不包含动态参数、敏感信息或自然语言，不拼接生成，不依赖枚举顺序或魔数；不得重复定义、未经批准重命名、复用废弃代码。内部错误与公开代码区分。多个底层原因归并时必须有明确业务归类关系，不掩盖安全边界、处理后果、必要上下文或原恢复逻辑；禁止全部归为 INTERNAL_ERROR。

## 第四章：Rust 强类型与唯一权威定义

所有公开错误代码集中在 **`src/error.rs`**，使用带显式固定整数值的 Rust enum 及穷尽匹配；每个错误代码必须有中文说明性注释。内部 Error 优先复用既有类型，不为命名无故重写。不得通过通配匹配隐藏新增类别、枚举索引推断代码或让多个模块维护代码字符串。新增代码必须触发一致性检查。代码定义、结构化协议、参数 Schema、文档和检查均从同一权威契约派生或严格互校。

## 第五章：结构化返回

复用既有 API/序列化框架，不更换通信架构。code 必须是稳定机器类别，不含文本或参数。params 只能包含登记且验证过的键，每键明确名称、类型、必填性、业务意义、长度/数值范围和安全限制。可选 trace_id 必须可靠生成，不使用指针或敏感信息；message 仅用于开发诊断，不是稳定判断依据。

错误对象不得改变 Result 的成功/失败。序列化、参数构造或诊断失败不得制造成功或未授权默认行为。不存在的参数、鉴权、IPC、日志能力不得虚构。

## 第六章：代码与后果分离

每项代码记录真实触发条件和现有处理后果。非法规则按原验证/事务契约拒绝；原子更新失败保留已有有效配置。权限错误拒绝执行敏感操作，资源错误拒绝超限操作，DNS 失败按已确认策略处理，不擅自 DIRECT。业务规范有歧义时标记待确认，不能照抄示例改变行为。

## 第七章：网络规则语义不变

错误改造不得无故改变 IP、DOMAIN、DOMAIN-SUFFIX、DOMAIN-KEYWORD、PORT/TRANSPORT、Local/Remote、REJECT、DNS 前后决策、Debug、去重、覆盖裁剪、匹配结果或出站选择。DIRECT、PROXY、REJECT 为策略；ERROR 为执行失败。规则 REJECT 不等于远端拒绝连接、DNS 失败或执行异常。发现原有异常默认放行必须独立登记，不在无规范下擅改。

## 第八章：Debug 安全边界

Debug 仅由经过认证和授权的本地 API 操作，不能进入配置、订阅、普通规则或持久化文件。核实真实认证/授权责任；不能用错误代码代替检查或虚构已实现检查。验证未授权、关闭状态、非法生命周期、预算、部分更新、成功误转换、正式规则回退及来源伪造。保持 API-only、生命周期 1–3600 秒、存储过期时间、到期丢弃、Debug 可覆盖正式 REJECT 的已确认契约，不新增权限入口。

## 第九章：公开信息与受控诊断

公开信息不得无条件包含密码、Token、私钥、节点凭据、敏感配置、未授权文件内容、指针、对象地址或不必要路径。上下文检查长度/类型。底层错误保留必要受控诊断，不能直接公开完整链；过滤针对真实敏感信息，不以全部 INTERNAL_ERROR 隐藏分类。不得声称恢复已丢失的原因。

## 第十章：Documentation 查询表

真实内核 Documentation 目录创建 UTF-8 标准 Markdown《错误代码查询表.md》，中文、可追溯、完整、没有虚构或遗漏。可用于查含义、模块、触发条件、参数、后果、源码、兼容性及独立审查。不得在错误目录重复创建互相冲突的查询表。

## 第十一章：查询表内容

必须包括体系用途/命名/分类/稳定性/兼容性/内部与公开区别；实际存在的分类；完整表格；复杂错误解释；参数 Schema；兼容性及维护约定。表格至少有错误代码、中文名称、所属模块、具体说明、触发条件、处理后果、参数、实际源码定位。权限、预算、配置事务、DNS、匹配、状态及并发语义需展开。各参数记录名称、类型、必填、业务意义和安全限制。

## 第十二章：文档质量

禁止用“规则错误”“网络错误”“内部错误”等空泛解释填表。每条必须核实具体来源、拒绝条件及实际后果；未查明项标记未验证，不能猜测源码位置、处理后果或已经完成的功能。

## 第十三章：自动一致性与兼容性

检查全部公开代码登记、重复、未定义、名称、分类、参数 Schema、说明、触发条件、后果、源码、废弃状态及已公开契约未经批准变更。采用唯一权威规范及受校验机器快照，允许生成或验证文档。新增代码未同步文档必须失败。数量相同不能证明语义正确，仍须独立审查映射。

## 第十四章：资源与异常

验证错误对象/参数/链/日志有界、格式化/序列化无不合理分配、不绕过 ByteBudget、失败释放临时资源、不保留无用快照、不破坏生命周期。重点覆盖内存不足、预算超限、整数溢出、长度、序列化、非法输入、锁中毒、快照异常、损坏文件及恢复失败。不能为详细诊断制造新资源耗尽。

## 第十五章：并发一致性

核实错误下部分更新、锁释放、快照/操作版本归属、并发替换、竞态错误丢失或重复、死锁、资源回收及失效快照继续使用。保持现有切换语义；原有并发缺陷独立登记，不借错误改造重写架构。

## 第十六章：兼容性

最小侵入，不无故改业务规范、分流、优先级、裁剪、DNS、权限、预算、快照、配置、持久化、API、已公开代码或既有后果。不得静默重命名、改义或删除代码。不兼容变更须报告原因、旧/新行为、范围、兼容策略、迁移及回滚；重大变更请求确认。无充分理由不加第三方依赖。

## 第十七章：测试

必须测试唯一性/稳定性/映射/整数转换/新增覆盖/已公开兼容性；结构化正常、缺参、非法/超长参数、未知字段、长度、序列化失败；配置/规则/DNS/连接/Debug/预算/状态/并发失败；敏感信息、权限/资源不会吞没、失败不 DIRECT/Continue、不绕过验证；原规则/DNS/Debug/预算/快照/事务回归；文档登记、重复、虚构、必要字段、Schema。不得删除有效测试、弱化断言、改业务预期或跳过关键测试制造通过。

## 第十八章：独立语义验证原则

编译、类型、Clippy、测试、集成、参考/差分一致均不是语义正确的充分证据。独立核实优先级、覆盖、异常、安全、内存、并发、数据、权限、代码真实性及后果。测试预期来源于已确认业务契约，不从生产实现推导；两实现共同违约仍是缺陷。代码/测试与契约冲突时改代码和测试，不改契约迎合测试。

重要发现必须给规范、文件位置、实际/预期行为、最小复现、方案和回归要求。分别标记已确认正确、已确认缺陷、潜在风险、未验证；静态推断不能包装为运行证据，未执行/未查调用链不能宣称通过或安全。

## 第十九章：L1–L4

- L1：实际执行适用的 fmt/check/Clippy 和项目静态检查。
- L2：实际执行完整/相关测试、错误契约、文档及兼容性检查。
- L3：独立验证真实错误、分类、传播、后果、无默认放行/权限/来源/预算绕过、错误与快照/真实原因一致；不能由 L1/L2 代替。
- L4：核验代码证据、测试记录、映射依据、修改、兼容性及未测；不能用主观结论代替实际证据。

## 第二十章：实施顺序

确认结构/根目录 → 完整审查现有体系 → 确认语义规范 → 扩展现有 Error/强类型代码 → 统一公开结构化返回 → 逐步修正映射且保持后果 → Documentation 查询表 → 自动一致性 → 测试 → L1–L4 → 修改与验收报告。可安全实施的直接完成；个别歧义不阻止其他工作，但不得推进依赖未确认规则的部分。

## 第二十一章：交付报告

必须提供实际文件清单、全部公开代码、Error/ErrorCode/映射/传播/序列化说明、协议及兼容性、查询表路径、登记/重复/遗漏/未定义/空说明/空触发/空后果数量、实际命令及结果、错误/API/配置/持久化/网络兼容性、L1–L4 证据、已知缺陷/潜在风险/未测/待确认。示例与中文注释同步维护。

## 第二十二章：验收

只有唯一稳定强类型代码、真实语义、结构化/受限参数、真实传播、不放行/绕过/泄密/改规则/擅改代码、完整正确查询表、自动检查可捕获遗漏、回归实际结果及可靠 L1–L4 证据均可确认，才可宣称任务完成。无法确认项必须逐条标未验证；不得用文档或测试一致替代语义验证。

## 第二十三章：执行纪律

必须实际检查、修改、测试和记录；最小侵入、契约优先、保持兼容、不引入无关重构、不改未确认规则、不降低安全/忽略异常/绕过预算、不伪造来源/代码/测试/完成、不削弱测试、不凭技术检查证明业务正确、不填空泛文档、不建冲突定义。每个新建、修改、废弃错误代码均同步代码、协议、测试、示例、注释及查询表。
