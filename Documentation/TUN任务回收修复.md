# F-02：TUN 运行期完成任务回收

作者：可莉唯一的狗。

## 缺陷与业务依据

原 UDP 接收流和 TCP 共用任务入口直接向 JoinSet 登记，运行期间没有消费完成记录；流表 retain 只移除 AbortHandle，不能释放 JoinSet 的历史完成节点。连续短流结束后，即使活动流数量始终很小，登记节点仍随会话总流数增长。违反 AGENTS/开发约定.md 的任务资源有界要求及会话生命周期规范第六条。

独立预期是：历史完成总量不能成为永久资源占用；回收不得取消其他活跃流；取消请求不能提前当作真实完成；关闭后的任务表为空、资源已释放，新登记被拒绝。

## 最小修复与边界

- src/tun/udp.rs：UDP/TCP/维护任务统一登记；登记前消费完成项；明确 MAX_SESSION_TASKS 为 128，包含尚未结束的取消任务；UDP 接收顺带回收。
- src/tun/tcp/session.rs：TCP 接收调用同一回收入口，不要求宿主额外调用清理 API。
- 回收仅使用 try_join_next，不等待和取消活跃任务；非取消的 JoinError 沿用现有 Internal 诊断，不改错误码、策略或单流错误队列。
- 关闭仍按原撤销、停止、等待、排空顺序完成；正常运行回收不替代关闭流程。
- 登记失败的 future 在权限锁、任务锁之外析构；真实 TCP Context 持有同一会话 Operation，满额拒绝时不能在权限回调内析构并重入同一锁。上限回归携带真实 Operation 验证此错误路径。
- 完全无调用时允许有界完成节点暂留，不能宣称立刻释放或把登记上限当作 RSS 上限；不新增后台循环、第三方依赖、配置字段或公开管理 API。

## 独立回归与示例

1. 512 个任务逐次完成，始终保留另一个活动任务；登记节点不随历史总量增加，活动任务未被取消。
2. 填满 128 个真实挂起任务，额外登记返回 8001；完成和取消后重新登记成功，并发关闭结束后表为空、析构计数归零。
3. 实际 UDP 48 条短流循环，每次新流提交后、接收回收前断言任务登记有界，防止接收端回收掩盖 UDP 入口遗漏。
4. 任务 panic 完成后产生一次受控诊断，第二次回收不重复记录。
5. 保留真实 TCP 流并反复回收完成任务，之后仍可发送 alive 并接收 ok。

可运行示例：examples/tun_task_lifecycle.rs。测试及真实同名报告位于 tests/test_tun_udp.*、tests/test_tun_tcp_session.*。

首轮针对测试中，新增 UDP 短流用例未显式配置 DIRECT，按默认 REJECT 被正确拒绝，出现一项失败；仅补全该用例的明确路由前提，不修改默认策略或既有断言。首轮证据保留于 /private/tmp/fluxa-f02-focused-evidence，后续执行结果与版本以同名测试报告为准。第二轮针对执行还暴露 panic 观察用例把 AbortHandle::is_finished 当成 JoinSet 通知已发布的时序假设；改为在两秒期限内轮询并确认真实 join 完成，再验证诊断恰好记录一次。保留诊断断言和失败证据 /private/tmp/fluxa-f02-focused-v2-evidence，不将该轮失败冒充通过。

## 验收范围

L1 核查类型、锁顺序及非阻塞回收；L2 通过统一执行器记录实际回归；L3 按以上独立资源和连接连续性契约核对，不能仅以编译/测试通过推断全部业务正确；L4 通过代码、同名报告及原始执行证据追溯。系统 TUN、真实设备、长期 RSS 压力与其他平台不在本轮回环验证范围，未验证项不计为通过。
