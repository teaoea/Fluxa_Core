# VPN 接管前置检查与事务化启动技术规范（MUST）

作者：可莉唯一的狗。

本规范是已确认的产品与开发约束，适用于 Rust 网络内核、App、Network Extension 及必要的平台适配。内核仓库的 `Documentation/VPN启动技术规范.md` 为共同规范，App 保存同文副本，修改时同步维护。本文规定后续实现和验收，不代表现有系统 TUN 已实现、已接管或已验证。

## 一、默认运行模式

| 模式 | 程序运行时的默认启动意图 |
| --- | --- |
| TUN 模式 | 默认启用，必须先通过本规范的检查和启动事务 |
| 系统代理 | 默认关闭 |
| 网关模式 | 默认关闭 |
| 局域网共享 | 默认关闭 |

默认启用不等于启动成功。启动过程中不得提前标记 TUN 已启用或内核 Running；缺少能力、权限、必要出站或有效授权时拒绝本次网络启动。App 可展示错误或二次确认，但不得因此接管网络。失败时不得自动启用系统代理、网关或局域网共享。

## 二、启动前必要检查

| 检查项目 | 必须满足的条件 | 失败处理 |
| --- | --- | --- |
| 配置文件 | `config.yaml` 语法、字段、格式版本和业务约束全部合法；拒绝未知字段、重复键和不支持的版本 | 拒绝启动 |
| 规则引擎 | 编译成功，优先级与覆盖关系符合既定规范；使用本次配置对应的完整有效快照 | 拒绝启动 |
| 代理节点 | 至少满足当前配置所要求的出站可用性条件，实际验证必要代理链路；无节点按第四、五节处理 | 不满足条件拒绝启动 |
| DNS | 必要解析组件和配置的必要上游可用 | 拒绝启动 |
| GeoIP | 未配置允许禁用；显式配置后必须成功加载 | 未配置 WARN 并保持禁用；已配置失败 ERROR，拒绝启动 |
| 资源预算 | 内存、文件描述符、缓冲区等满足要求，包括启动临时数据、旧状态与新状态共存的峰值 | 拒绝启动 |
| 权限 | 具备启动 VPN 所需的系统权限 | 拒绝启动 |
| 系统环境 | Network Extension 与必要系统能力可用 | 拒绝启动 |
| 路由保护 | 代理出站连接不会因接管而形成路由回环 | 拒绝启动 |
| 生命周期 | 没有冲突的启动、停止或接管事务 | 拒绝冲突操作，不破坏现有有效状态 |

必要链路范围由合法配置和实际路由需求确定，不能把“至少一个节点有响应”替代所有必要出站条件。节点配置存在、进程存活或监听端口存在均不是可用性的充分证明。所有探测须有截止时间、取消和资源上限，不得为了测试可用性而绕过既定 DIRECT 规则或防泄漏策略。

## 三、《VPN 接管前置检查与事务化启动原则》（MUST）

1. Rust 网络代理内核必须执行启动前置检查，未经检查通过不得激活 VPN 网络接管。
2. 启动流程必须明确区分 Preflight、Prepare、Commit、Verify 四个阶段。
3. 前置检查必须验证配置、规则、必要代理链路、DNS、资源预算、权限及系统运行条件。
4. GeoIP 未配置时记录 WARN 并保持禁用；显式配置后初始化失败必须返回 ERROR，阻止本次启动。
5. 禁止以节点配置存在、进程存活或监听端口存在作为代理可用性的充分证明。
6. 禁止在必要的出站能力尚未准备好时接管 VPN。
7. VPN 接管必须具备明确的失败回滚与状态恢复机制。
8. 接管后必须验证 TUN、路由、DNS 及代理转发数据路径。
9. 接管后验证失败，不得将内核标记为 Running。
10. 回滚失败必须报告独立错误，并保留真实系统状态。
11. 启动、停止、取消及重复启动操作必须具有明确的并发和幂等性约束。
12. 禁止启动失败时擅自切换为系统代理、网关模式或局域网共享。
13. 禁止错误处理造成非预期 DIRECT、路由回环或权限绕过。
14. 所有启动错误必须使用统一的四位数字错误代码，并登记到《错误代码查询表.md》。
15. 必须按照《代码审查独立语义验证原则》和《不可信输入与信任边界验证原则》进行独立验证。

### 四阶段及回滚边界

| 阶段 | 必须完成的工作 | 系统接管边界 |
| --- | --- | --- |
| Preflight | 严格解析和业务校验、规则编译、必要链路与 DNS 探测、GeoIP、预算、权限、系统能力、路由保护、生命周期检查；无节点时取得本次可信授权 | 不接管网络，不发布 Running |
| Prepare | 固定本次配置和规则快照，准备出站、解析器和有界资源；保存必要系统原状态与回滚信息，复核授权及检查结果仍有效 | 不接管网络；准备失败释放本次资源，保留原状态 |
| Commit | 在受控事务中应用 TUN、路由和 DNS 接管；每个系统变更有明确所有者、顺序与逆向恢复操作 | 允许实际接管，但仍不是 Running |
| Verify | 验证实际 TUN 收发、路由防回环、DNS 和配置所要求的直连/代理数据路径；无节点经授权时验证 DIRECT 路径，不伪造代理成功 | 全部必要验证通过才发布 Running；失败或取消进入回滚 |

检查结果与授权必须关联同一次启动、配置状态和适用系统状态。配置、节点、规则、权限或系统条件变化使证据失效时，重新检查；无节点确认绑定失效时重新确认，不能直接继续 Commit。

启动事务由 Rust 统一管理配置、规则、网络处理、资源和状态机。Swift 只负责可信的本地确认 UI 及必须使用 Apple API 的权限、Network Extension、TUN 包读写和系统设置；平台检查结果必须返回 Rust 并通过当前事务的受约束接口验证，配置或订阅不能伪造权限、授权或系统成功状态。

启动、停止和取消必须串行化或明确拒绝冲突操作，重复调用不得重复接管或重复释放。取消必须传播至探测、准备、提交和验证阶段；中途退出、扩展失联或阶段失败必须有可验证的恢复路径。恢复不得盲目覆盖其他主体之后修改的系统设置。

回滚应恢复本次事务改变的路由、DNS、接口及其他必要系统状态，并释放本次资源。必须分别报告原始启动故障和回滚故障；回滚失败时保留可观测的真实接管状态、尚未恢复项及可执行的恢复入口，不能宣称已停止、已恢复或 Running。启动前已存在的有效运行状态，不得因新事务失败而被无理由破坏。

## 四、代理节点状态与接管资格

| 代理节点状态 | 启动行为 | 是否允许接管 VPN |
| --- | --- | --- |
| 未配置任何代理节点 | 要求二次确认 | 确认后且其他必要检查通过才允许 |
| 配置了节点，但全部无效 | ERROR，禁止启动 | 不允许 |
| 配置了节点，但必要代理链路不可用 | ERROR，禁止启动 | 不允许 |
| 配置了节点，且必要链路验证成功 | 正常启动 | 其他必要检查通过后允许 |
| 用户拒绝二次确认 | 取消启动 | 不允许 |
| 二次确认超时 | 取消启动 | 不允许 |

“无节点”不能通过丢弃无效节点、忽略订阅错误或过滤失败链路伪造。完全无节点与已配置但无效或不可用属于不同结果。

## 五、《无代理节点启动二次确认原则》（MUST）

1. VPN 接管前必须检查代理节点配置及必要出站链路的可用性。
2. 完全没有配置代理节点时，必须进入用户二次确认流程，不得自动接管 VPN。
3. 二次确认必须明确告知 DIRECT 连接可能暴露真实公网 IP 的风险。
4. 用户拒绝、取消或确认超时，必须终止本次启动，不得接管 VPN。
5. 用户明确确认后，允许继续启动，但仍必须通过其他所有必要前置检查。
6. 已配置代理节点但必要链路不可用时，必须返回 ERROR，禁止自动降级为 DIRECT。
7. 二次确认必须来自可信的本地授权路径，不得由不可信配置或订阅伪造。
8. 授权必须绑定本次启动及配置状态，不得无限期复用。
9. 确认后不得跳过 TUN、DNS、路由、规则引擎和资源安全检查。
10. 无论是否存在代理节点，内核都必须遵守既定 DIRECT 规则与防泄漏策略。
11. 二次确认发生在 VPN 实际接管之前，不得先接管网络再等待确认。
12. 所有拒绝、确认失效和启动失败状态必须明确区分，并纳入统一错误或状态体系。

### 本地确认示例与授权约束

确认提示示例：“当前未配置代理节点。继续启动后，DIRECT 连接可能暴露你的真实公网 IP。是否继续本次 VPN 启动？”必须提供明确的继续与取消操作；没有回答不代表同意。隐私协议的一揽子同意不能替代此次确认。

确认请求和授权有明确有效期，并绑定本次启动标识及配置状态；授权只用于本次启动，终止、取消、超时、配置变化或使用后不得复用。不可信 YAML、订阅、缓存、IPC/API 或 FFI 输入不能直接提供可被信任的“已确认”布尔值；程序必须核实来自受保护本地授权路径的本次有效授权。具体授权载体和超时值由实现定义并配套边界测试，不在规范中伪造已存在的 API 或配置字段。

## 六、错误、状态与信任边界

公开错误使用内核 `src/error.rs` 集中定义的显式固定四位整数（1000–9999），遵循内核 `Documentation/错误代码体系设计.md`。新增、修改或废弃代码必须登记到 `Documentation/错误代码查询表.md`，同步参数 Schema、真实触发条件、处理后果、调用方与自动一致性/兼容性检查。不得在 App 中由错误文本拼接或推断错误码。

至少明确区分：等待确认、用户拒绝、用户取消、确认超时、授权失效、前置检查失败、准备失败、接管失败、接管后验证失败、回滚失败、生命周期冲突和验证成功。用户拒绝与规则 REJECT、技术执行故障不能混同；正常等待确认不是 Running。状态与诊断不能伪造成功或触发非预期 DIRECT。

本次仅登记强制规范，不分配不存在的错误代码，不将未实现状态写入已实现错误查询表。WARN/ERROR 是必须保留的诊断语义；本次不开发日志设施。

必须检查配置、订阅、DNS/网络、文件/缓存、持久化恢复、IPC/API、FFI/系统接口及本地授权的输入与信任边界。所有输入有大小、数量、时间和资源上限；校验失败在产生接管副作用前明确拒绝，不得 panic、失控分配、绕过权限或把错误变成 DIRECT。持久化的“上次确认”或“上次 Running”不能直接充当本次有效证据。

## 七、独立语义验收与交付证据

执行《代码审查独立语义验证原则》：以本规范与既定路由规范独立确定预期，再检查实际代码及调用链。编译、参考匹配器、差分一致或两个实现相互一致都不能替代业务语义验证。审查必须区分已确认正确、已确认缺陷、潜在风险和尚未验证。

执行《不可信输入与信任边界验证原则》：逐项记录校验入口、可信依据、失败代码或状态、真实系统后果与测试证据；重点验证配置和订阅不能伪造本地确认、权限、节点可用性或系统接管成功。

最低验收矩阵包括：

- 四种默认模式；未验证时不得显示已启用或 Running；失败不得切换其他模式。
- 各前置检查逐项失败；配置非法、规则编译失败、必要 DNS 不可用、预算不足、权限拒绝、系统能力缺失和路由回环均不接管。
- GeoIP 未配置保持禁用并产生 WARN；显式配置无法加载产生 ERROR 并拒绝启动。
- 无节点确认、拒绝、取消、超时、过期、配置变化、跨启动重放和不可信输入伪造；接管前的授权必须真实有效。
- 有节点但全部无效、必要链路失败、仅进程或端口存在；不得降级 DIRECT，也不得伪装成无节点。
- Prepare、Commit、Verify 各阶段故障或取消；部分系统变更回滚、回滚本身失败、中途退出与重新启动恢复。
- 启动/停止/取消并发及重复调用，资源释放、原有效状态保留及系统状态被其他主体修改的情况。
- 接管后真实 TUN、路由、DNS、代理或经授权 DIRECT 数据路径；未经真实验证不得发布 Running。

L1 静态检查、L2 测试与一致性检查、L3 独立业务语义核实、L4 实际证据分别记录。真实系统 VPN、最低/最新目标系统及真机不可用时明确标为未测，不以回环诊断、编译或发布替代验收。实现与交付仍遵循现有七步流程；本规范本身不授权恢复暂停任务、发布内核或合并 main。
