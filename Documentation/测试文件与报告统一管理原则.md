# 《测试文件与报告统一管理原则》

- **规范等级**：MUST（强制执行）
- **适用对象**：Rust 网络代理内核及其测试、测试报告、自动化测试和代码审查工作流
- **唯一测试目录**：项目约定的根目录 `tests/`（全小写）
- **适用阶段**：开发、重构、缺陷修复、回归验证、合并审查及正式发布
- **核心要求**：测试与报告同目录、同名主体、真实执行、可追溯、独立语义验证

> 本规范是项目的强制工程约束；不得因 AI 生成代码、快速迭代、`dev` API 不稳定或测试通过而放宽安全及业务语义要求。文中示例用于展示规范与注册方式，除明确引用的现有代码接口外，不代表项目已存在示例 API、测试、错误代码或执行结果。

## 第一章　目标与基本原则

### 第一条　统一管理

1. 所有项目测试源文件和对应的 Markdown 测试报告 **MUST** 集中保存在唯一的根目录 `tests/`。
2. **MUST NOT** 额外创建 `Tests/`、`test/`、`Reports/`、`tests/Reports/`、`tests/Unit/`、`tests/integration/` 等用于容纳本规范所述测试或报告的目录。
3. **MUST NOT** 将对应 Markdown 报告散放在 `src/`、项目根目录、其他模块目录或多个报告目录中。
4. 测试文件的存在不等于测试已注册、已执行或已通过；测试报告的存在也不等于对应代码目前仍然有效。
5. 测试预期 **MUST** 来自独立、明确的业务契约，**MUST NOT** 从当前生产实现的输出反向生成预期值。

### 第二条　真实性

1. 报告中所有执行事实 **MUST** 有相应的真实运行证据。
2. **MUST NOT** 伪造测试命令、时间、提交版本、执行数量、覆盖范围或通过结论。
3. **MUST NOT** 通过删除失败测试、弱化断言、擅自标记忽略或修改预期值掩盖实现缺陷。
4. 编译成功、测试通过以及测试报告生成，均不得替代独立业务语义审查。

## 第二章　唯一目录与文件命名

### 第三条　目录结构

项目采用以下唯一布局：

```text
<项目根目录>/
├── Cargo.toml
├── src/
│   ├── routing/
│   │   ├── flat.rs
│   │   └── index.rs
│   └── budget.rs
└── tests/
    ├── test_routing_flat.rs
    ├── test_routing_flat.md
    ├── test_routing_index.rs
    ├── test_routing_index.md
    ├── test_budget.rs
    └── test_budget.md
```

上述文件列表是命名和目录结构示例，不表示项目目前已经存在这些测试或报告。

### 第四条　测试文件命名规则

1. 对应 `src/` 下的源文件，去除 `src/` 前缀与末尾 `.rs`。
2. 将路径分隔符 `/` 转换为下划线 `_`。
3. 在结果前加 `test_`，最后加 `.rs`。
4. 路径映射 **MUST** 使用真实源文件名，不得擅自单复数变换、缩写、重命名或增加非规范后缀。
5. 测试文件及报告文件 **MUST** 使用全小写的规范名称；同一测试套件的报告名仅将 `.rs` 改为 `.md`。

| 源文件                 | 测试文件                      | 报告文件                      |
| ---------------------- | ----------------------------- | ----------------------------- |
| `src/routing/flat.rs`  | `tests/test_routing_flat.rs`  | `tests/test_routing_flat.md`  |
| `src/routing/index.rs` | `tests/test_routing_index.rs` | `tests/test_routing_index.md` |
| `src/dns/resolver.rs`  | `tests/test_dns_resolver.rs`  | `tests/test_dns_resolver.md`  |
| `src/budget.rs`        | `tests/test_budget.rs`        | `tests/test_budget.md`        |

`src/routing/flat.rs` 与 `src/routing/flats.rs` 是不同路径，分别映射为 `test_routing_flat.*` 与 `test_routing_flats.*`；不得混用。

### 第五条　命名冲突与特殊测试

1. 如果两个真实源码路径在上述扁平化后映射为同名文件（例如 `src/a_b/c.rs` 与 `src/a/b_c.rs`），或多个 Cargo 包具有同名源码路径，**MUST** 在创建前识别并报告冲突，不得覆盖任何已有测试或报告。
2. 命名冲突不能靠静默改名解决；**MUST** 先取得针对该冲突的明确命名决策，并登记例外对应关系。
3. 跨模块集成测试或端到端测试如不属于单一源文件，**MUST** 使用稳定、唯一、以 `test_` 开头的业务契约标识，并在头注释与报告中准确列出涉及的模块和业务契约；不得虚构对应的单一 `src` 文件。
4. 删除或重命名源码时，**MUST** 同步核查测试文件、报告、Cargo 注册路径与映射登记；不得留下被误认为仍有效的孤立文件。

## 第三章　测试类型与文件头

### 第六条　测试类型分类

1. **执行机制类型**必须明确标识为“单元测试”或“集成测试”；其他实际适用的标识可以作为测试属性补充，例如“回归测试”“安全测试”“并发测试”“资源预算测试”“性能测试”。
2. “回归测试”“安全测试”等描述测试目的，**不得**将它们误认为 Cargo 自动识别的独立执行机制。
3. 具有性能、压力或基准测试性质的测试，**MUST** 明确其运行条件、判断阈值和测试工具，不能因为一次普通单元测试通过就宣称性能指标达标。

### 第七条　文件头强制字段

每个 `.rs` 测试文件开头 **MUST** 使用 `//!` 文件级注释，至少包含以下字段：

- 测试文件：相对于项目根目录的实际路径；
- 测试类型：实际执行机制类型和适用的测试属性；
- 测试对象：真实源码路径或明确的跨模块业务契约；
- 测试内容：当前实际存在的测试函数及独立验证目标；
- 测试依据：明确的业务规范、数据格式规范、接口契约或安全约束；
- 前置条件：需要特殊环境、权限、网络、数据文件或测试桩时列明。

文件头 **MUST** 与测试代码保持一致，**MUST NOT** 将尚未实现、没有有效断言、未注册或仅计划编写的测试描述为已经覆盖。

### 第八条　测试头注释与真实代码示例

以下例子只验证已知的平铺索引空缓冲区拒绝语义，不声称覆盖整个索引校验、规则优先级或内存预算：

`src/routing/flat.rs` 中注册：

```rust
#[cfg(test)]
#[path = "../../tests/test_routing_flat.rs"]
mod test_routing_flat;
```

`tests/test_routing_flat.rs` 内容：

```rust
//! 测试文件：tests/test_routing_flat.rs
//! 测试类型：单元测试、非法输入回归测试
//! 测试对象：src/routing/flat.rs
//!
//! 测试内容：
//! 1. test_reject_empty_flat_index：空索引缓冲区必须被判定为无效输入。
//!
//! 测试依据：
//! - 平铺索引格式的文件头最小长度约束。
//! - 《不可信输入与信任边界验证原则》。
//! 前置条件：无外部服务依赖。

use super::*;

#[test]
fn test_reject_empty_flat_index() {
    let actual = FlatIndex::parse(Vec::new(), &[]);
    assert!(matches!(actual, Err(Error::InvalidInput)));
}
```

说明：此示例基于已提供的 `flat.rs` 中 `FlatIndex::parse` 与 `Error::InvalidInput` 的接口形态；仅示范一种可验证的边界断言，**不代表该测试已经在实际项目编译或执行**。不得仅为测试修改生产 API 可见性。

### 第九条　同步维护

1. 新增、删除、重命名测试函数或修改断言目标时，**MUST** 同步核对头部“测试内容”。
2. 如果多个测试函数共同覆盖一个场景，说明必须能够追踪到真实测试函数。
3. **MUST NOT** 用含糊的“全面覆盖”“所有安全场景均已验证”等语句代替实际覆盖描述。
4. 自动扫描可以验证函数名是否存在，但不能独立证明其断言充分性；后者 **MUST** 通过语义审查判断。

## 第四章　Cargo 测试注册与执行

### 第十条　禁止依赖偶然发现

1. `tests/` 是 Cargo 默认集成测试发现目录，根目录中的 `.rs` 文件可能被自动作为独立集成测试目标。
2. 本项目允许在同一 `tests/` 中保存按源码映射的单元测试文件，**MUST** 显式解决 Cargo 的自动发现冲突。
3. 如果采用本文推荐的集中单元测试注册方式，须在相应 Cargo 包的 `[package]` 中配置：

```toml
[package]
autotests = false
```

这是 `[package]` 内的属性，示例并非要求覆盖现有 `Cargo.toml` 的其他内容。

1. 该配置关闭自动发现集成测试目标，**不关闭**正确注册的库/二进制单元测试；需要执行的集成测试 **MUST** 通过 `[[test]]` 显式注册。

2. 如果项目采用不同而实际可靠的 Cargo 注册方式，必须证明不会重复编译、重复执行或遗漏测试，并在规范例外中记录。

### 第十一条　单元测试注册

1. 单元测试源文件必须在正确的生产模块中通过 `#[cfg(test)]` 加 `#[path]` 显式注册，或使用具有等价可验证效果的注册机制。
2. **MUST** 核对 `#[path]` 与测试文件在真实包布局中的相对关系；Rust 文件移动后必须同步更新。
3. 测试不应因为放置在 `tests/` 而自动被当成只能访问公开 API 的集成测试。
4. **MUST NOT** 为了测试内部函数而将 `private`、`pub(super)` 或 `pub(crate)` 不必要地扩大为公开 `pub`。
5. 若源模块已有同名子模块，注册时必须选择不冲突的测试模块名。

### 第十二条　集成测试注册

跨模块集成测试应基于公开且授权的接口验证真实契约，示意配置：

```toml
[[test]]
name = "test_routing_integration"
path = "tests/test_routing_integration.rs"
```

只有在相应测试文件确实存在、内容完整且项目确认需要该集成目标时才能加入该配置。不得为了使集成测试编译通过而不必要地公开内部资源管理接口。`autotests = false` 后未显式注册的集成目标不会自动执行。

### 第十三条　工作区及实际发现检查

1. Cargo Workspace 中的“包根目录”和“工作区根目录”可能不同；集中 `tests/` 的路径和所有注册声明 **MUST** 以实际包结构验证，不得假定相对路径自动正确。
2. 必须使用实际 Cargo 测试发现/执行结果验证测试已注册；仅扫描到 `.rs` 文件不构成执行证据。
3. `cargo test` 是否运行了指定功能测试、忽略测试、文档测试、全部包和 Feature 组合，取决于命令参数与项目配置；报告 **MUST** 写明实际范围。
4. 有条件跳过（平台、权限、环境变量、特性门控）的测试必须明示，不得冒充通过。

## 第五章　测试用例与独立验证要求

### 第十四条　有效测试的最低条件

每个计入有效覆盖范围的测试 **MUST** 至少具备：

1. 可辨识的测试目标和业务契约；
2. 明确构造的输入或状态前提；
3. 与生产实现独立的预期结果；
4. 真正执行目标逻辑；
5. 能在错误行为下失败的有效断言；
6. 必要的隔离、清理和确定性控制。

空测试、无断言占位测试、只打印日志而不校验的测试，以及由生产实现反向生成预期的测试，**MUST NOT** 计入已验证覆盖。

### 第十五条　核心安全与业务测试范围

根据实际模块风险，应当覆盖并记录：

- 非法、缺失、未知、重复、超长和矛盾输入；
- 数值边界、整数溢出、长度限制、递归深度和资源预算；
- 权限认证、可信来源、越权、重放、授权过期及本地 IPC 信任边界；
- 规则类别优先级、Debug 与普通规则关系、REJECT/DIRECT/PROXY 语义及无声跳过；
- TUN/VPN 接管前置检查、启动失败拒绝接管、启动后验证和异常恢复；
- 无代理节点时的明确用户风险确认与有节点但链路不可用时的禁止静默直连；
- GeoIP 未配置的合法禁用状态，与显式配置后失败的错误状态；
- 会话关闭、旧解析器/快照引用残留、绑定释放和并发重建；
- DNS、IPv4/IPv6、UDP/TCP、缓存一致性、数据完整性与异常流量；
- 并发取消、重复调用、状态竞争、快照原子切换及资源泄漏。

这些是**按风险选择的审查与测试清单**，不意味着每个单独测试文件必须覆盖所有项目，也不能在未实际测试时声称已经覆盖。

### 第十六条　测试隔离与清理

1. 测试不得擅自接管真实系统 VPN、改变系统代理、开放局域网监听或执行可能影响用户网络安全的高风险操作。
2. 需要真实系统接管、权限或网络环境的测试，必须有受控执行环境、明确的授权和完整回滚策略。
3. 共享端口、临时文件、系统网络状态、Mock 服务和 IPC 端点应避免并发冲突；清理失败必须显示记录。
4. 测试不得依赖不受控制的外部网络服务来证明纯本地业务语义，除非该测试明确属于外部集成验证。

## 第六章　Markdown 报告命名与生成

### 第十七条　一一对应

1. 每个按规范创建并执行的 `tests/test_<名称>.rs`，其权威 Markdown 报告 **MUST** 为 `tests/test_<名称>.md`。
2. `.rs` 和 `.md` 只允许扩展名不同，文件名主体必须一致。
3. 同一目录下不得建立多份不同命名的“最终版”“最新版本”“修复版”报告混淆权威结果。
4. 报告必须说明对应的是**最近一次实际执行**，还是因代码变更而处于**历史结果／待重新执行**状态。

### 第十八条　生成触发与失败保全

1. 每次针对某测试文件完成正式测试运行后，**MUST** 同步生成或更新对应 `.md` 报告。
2. **MUST** 在测试通过、断言失败、测试编译失败、超时、可捕获的中断或测试框架失败时尽可能生成报告，且保留真实退出状态。
3. 编译失败时可记录“编译失败，测试函数未执行”；不得将其虚报为“断言失败 N 项”，更不得报告“全部通过”。
4. 未实际运行时，**MUST NOT** 填写“PASS”“全部通过”或编造测试耗时；可保留原历史报告但必须标示其对应旧代码和旧时间。
5. 对于断电、进程被强制终止等无法执行报告生成器的情况，后续 CI/审查必须识别“执行证据或报告缺失”，不得假定测试成功。
6. 报告生成器必须在可控的失败收尾阶段运行；生成报告不能掩盖测试工具原本的非零退出码。

### 第十九条　局部执行与完整执行

1. 只运行筛选后的部分测试时，报告必须注明测试过滤条件、已执行项目及未执行范围，并将总体范围标记为“部分执行”。
2. **MUST NOT** 因少量测试通过而将整个测试文件报告标记为“全部通过”。
3. 如果一次运行涉及多个测试文件，必须根据可靠的测试归属映射分别生成或更新对应报告；无法确定归属时须记录未能归属，不得随意分配结果。
4. 测试重试必须记录次数、每次结果和最终判断；不得仅保留最后一次通过而隐去此前失败。

## 第七章　报告内容与状态模型

### 第二十条　最低报告字段

每份 Markdown 报告至少包含：

1. 测试报告名称及对应测试文件相对路径；
2. 测试对象（源文件或跨模块业务契约）；
3. 测试执行机制类型及其他实际测试属性；
4. 对应包名、Cargo 目标、测试命令、过滤条件及 Feature 组合；
5. 执行时间（带时区的 ISO 8601）与实际耗时；
6. 操作系统、CPU 架构、Rust/Cargo 版本及必要运行环境；
7. Git Commit、工作区是否有未提交修改，以及 CI Run ID（如有）；
8. 总体执行状态和测试进程退出状态；
9. 实际发现／实际执行／通过／失败／忽略／未执行的项目数（能确认的才填写）；
10. 与测试头注释对应的实际用例名称、独立目标和执行结果；
11. 每个失败或异常的触发条件、预期与实际、错误信息及最小复现信息；
12. 相关日志、机器可读证据或 CI 工件的可追溯标识；
13. 未覆盖范围、环境限制、已知缺陷及下一步处理；
14. L1–L4 独立审查实际状态；
15. 最终结论和该结论适用的确切范围。

### 第二十一条　统一状态定义

- **PASS**：本次实际执行且已达到明确断言要求；
- **FAIL**：实际执行后断言未达到预期；
- **IGNORED/SKIPPED**：根据测试框架或执行策略明确跳过，未验证目标；
- **NOT RUN**：未执行，不能评价结果；
- **COMPILE ERROR**：测试构建失败，测试用例未进入正常执行；
- **TIMEOUT**：运行超时，未能证明通过；
- **INTERRUPTED**：运行异常中断，结果不完整；
- **PARTIAL**：仅执行部分已定义范围；
- **STALE**：报告对应的代码或配置与当前待评估版本不一致；
- **UNKNOWN**：证据不足以判断，不得自动归为通过。

上述状态是**测试报告状态标签**，**不是**内核统一四位数字 `ErrorCode`，不得擅自创建或重新定义生产错误代码。

### 第二十二条　Markdown 报告固定模板

`tests/test_routing_flat.md` 的结构模板如下；尖括号占位内容只有在取得真实证据后才允许替换：

```markdown

- 测试范围：<实际执行范围>
- 测试命令：<实际命令及参数>
```

## 第八章　历史记录与可信证据

### 第二十三条　最新报告与历史保全

1. `tests/test_<名称>.md` 作为该测试文件最新一次执行的权威报告，保持固定路径以便检索。
2. 同一报告更新前，应保留可追溯的既有 CI 日志、机器可读结果或提交历史；历史执行证据允许保存在 CI 工件存储系统中，不要求在仓库新增测试报告目录。
3. 报告必须记录足以定位原始执行证据的 CI Run ID、提交或工件引用。
4. **MUST NOT** 通过覆盖最新报告抹去已知失败、重试、限制或未解决问题的历史证据。
5. 缺少历史记录机制时，必须明确说明该限制；不得虚称可以审计所有历史运行。

### 第二十四条　代码版本一致性

1. 报告必须标识实际测试代码的 Git Commit；有未提交修改时，必须额外标记 `dirty` 并说明结果不是对纯净提交的验证。
2. 发生会影响测试结论的生产代码、测试断言、Feature、工具链或配置变化后，旧报告不得自动被视为当前代码通过。
3. **MUST** 将未重新执行的报告标记为 `STALE`，或通过受控流程重新运行并更新。
4. **MUST NOT** 在没有运行测试的情况下，仅修改 Git Commit 字段把历史通过记录包装为新版本通过。

## 第九章　CI 与质量门禁

### 第二十五条　CI 强制检查

CI 至少应检查：

1. 根目录只采用约定的 `tests/` 存放测试及对应报告；
2. `.rs` 与 `.md` 文件名主体一致且符合 `test_` 规则；
3. 可映射测试对应真实源码或登记的跨模块契约；
4. 文件头存在且测试类型、对象、内容、依据齐全；
5. 测试文件已正确注册，实际能够由 Cargo 执行；
6. 未启用意外的自动发现、重复执行或遗漏；
7. 报告对应实际执行、代码版本、测试范围和退出状态；
8. 失败、超时、编译错误及异常中断没有被报告生成流程掩盖；
9. 没有因测试要求而不必要地扩大生产公开 API；
10. 不存在虚报覆盖、占位测试计入通过或静默忽略失败用例；
11. 项目已定义的独立安全与业务语义审查门禁得到保留。

### 第二十六条　测试与报告生成器的执行契约

1. 执行器 **MUST** 保留 Cargo 测试进程的原始退出码。
2. 报告生成器 **MUST** 在可捕获的执行失败后仍尝试生成失败或未完成报告。
3. 报告生成器失败 **MUST** 使相应质量门禁失败，不得被解释为测试通过。
4. 可以采用 CI 的 `always()` 收尾阶段、Shell 退出处理或等效可靠机制；不得假定 `cargo test` 自动产出 Markdown。
5. 必须避免因管道 `tee`、命令链 `|| true`、错误捕获逻辑或重试脚本覆盖真实失败状态。
6. CI 通过必须同时满足实际测试要求和报告证据要求；**MUST NOT** 因报告生成成功而忽略测试失败。
7. 不应只依赖标准输出中文本计数来猜测测试归属；必须建立明确的测试目标/模块与报告文件映射。

## 第十章　版本分支与发布约束

### 第二十七条　dev 分支

1. `dev` API 不稳定，可按正确业务契约重构或删除；但相关测试 **MUST** 与实际实现同步维护。
2. **MUST NOT** 因 API 不稳定而免除测试真实性、安全边界、资源预算和规则语义验证。
3. 删除旧 API 后，不应继续保留只为未发布兼容而存在的无效测试；删除或更新测试时，必须如实说明覆盖范围变化。

### 第二十八条　main 与 crates.io

1. `main` 已正式发布公开 API 的不兼容修改仍须明确授权，相关回归测试必须验证正式兼容契约。
2. 只有来自经审查的 `main` 正式版本允许发布到 crates.io；`dev` 代码禁止发布。
3. crates.io 发布前必须检查与该版本对应的真实测试结果及报告追溯性；测试通过不自动证明业务语义兼容。
4. 已废弃 API 的过渡期与编译警告测试必须遵守项目《API全生命周期管理》规范；未经授权不得借清理测试绕过 API 迁移保护。

## 第十一章　业务语义与信任边界审查

### 第二十九条　L1–L4 分级

每次正式审查应分别给出以下结论，不得互相替代：

- **L1 静态正确性**：边界、类型、内存、并发与潜在 Panic 等；
- **L2 实现与测试一致性**：测试是否真实执行，断言是否验证目标行为；
- **L3 独立业务语义验证**：以权威需求为准，检查规则优先级、故障处理、授权和资源生命周期；
- **L4 证据验证**：提交、执行命令、日志、重试及报告结论能否互相核验。

未开展的层级 **MUST** 标注“未验证”，不得自动写成“通过”。

### 第三十条　不可信输入与高风险情况

1. 测试输入、生成的缓存/索引、外部网络响应、持久化数据、IPC 消息及测试工具输出都必须按其真实信任级别处理。
2. 禁止仅因解析成功、类型匹配或编号合法，就推定业务语义正确。
3. 规则优先级、Debug 临时覆盖、认证权限和来源标签必须由独立业务契约决定，不得因测试框架方便而改变。
4. 高风险缺陷应给出可复现输入、实际行为、期望行为、源码位置、修复与回归测试；证据不足时标记“潜在风险”或“待验证”。

## 第十二章　违规处理与验收标准

### 第三十一条　必须阻止合并或发布的情形

出现任一情况时，相关测试质量门禁 **MUST** 判定不通过：

- 文件命名或唯一目录规范未满足且无明确例外；
- 测试文件未注册或实际未执行却声称通过；
- 文件头声称的测试内容与实际代码不一致；
- 没有真实执行证据却生成通过报告；
- 测试失败但最终退出状态被错误转换为成功；
- 报告与当前待验证代码版本不一致，却声称有效；
- 为通过测试而削弱断言、隐藏失败或扩大内核无必要公开 API；
- 违反已确认的权限、安全、规则优先级或资源生命周期约束；
- 重要审查层级未执行，却伪造为通过。

### 第三十二条　完成定义（Definition of Done）

对涉及测试的开发任务，只有同时满足以下条件，才可声明测试交付完成：

1. 相关测试源码位于唯一 `tests/`，命名规范正确；
2. 文件头准确描述真实类型、测试对象、实际测试内容与依据；
3. Cargo 注册、执行机制和测试范围已核验；
4. 已运行应执行的测试，并保留真实结果和退出状态；
5. 相应同名 `.md` 报告已根据本次实际运行同步生成或更新；
6. 失败、跳过、未执行及限制均得到诚实记录；
7. 当前提交、工作区状态、测试命令、环境和原始证据可追溯；
8. 已按任务要求完成独立业务语义审查，未完成部分如实标记；
9. 未违反内核自治、最小公开 API、资源预算和零信任边界要求。

## 第十三章　最终强制约定

> **唯一目录**：仅使用小写 `tests/`，测试代码和对应 Markdown 报告放在同一目录。  
> **统一命名**：`src/routing/flat.rs` → `tests/test_routing_flat.rs` → `tests/test_routing_flat.md`。  
> **文件头**：必须明确测试类型、测试对象、实际测试项目、验证依据及必要前置条件。  
> **Cargo 注册**：必须证明测试可实际执行；集中单元测试不得被误作为独立集成测试；禁止为测试扩大生产公开 API。  
> **同步报告**：真实运行后生成同名 `.md`；失败也必须生成可核验证据，且不能掩盖失败退出状态。  
> **结果真实**：跳过、未执行、编译失败、超时、局部执行和旧版本报告均不得冒充全部通过。  
> **独立审查**：L1–L4 分别记录；测试通过不代表业务语义已被证明。  
> **内核优先**：任何测试便利措施都不得破坏 Rust 内核独立生命周期管理、公开 API 最小化或安全信任边界。  
> **变更管理**：本规范的强制约束不得由 AI 擅自修改、放宽或绕过；涉及目录和命名约定的例外须先取得明确授权。
