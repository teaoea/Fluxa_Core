# TCP 窗口扩大协商

作者：可莉唯一的狗。范围：dev 的自研 TCP 数据包会话；不代表系统 VPN 或正式二进制已交付。

## 协商及数据路径

遵循 [RFC 7323](https://www.rfc-editor.org/rfc/rfc7323.html)：只从 SYN 读取 Window Scale，
合法长度且 shift 大于 14 的输入按 14 使用。非 SYN 上合法格式的 WS 忽略，不修改既有协商；
长度错误或重复 SYN WS 明确拒绝。不会把选项长度、枚举序号或自然语言作为路由依据。

对端未提供 WS 时保持原 32 KiB 接收环及原窗口行为，SYN-ACK 不擅自提供 WS。
对端提供 WS 时，回复本地 shift=2，接收环为 128 KiB。SYN/SYN-ACK 的 16 位窗口不缩放，
握手确认完成后的窗口才按双方各自 shift 解释；后续不重复发送 WS 选项。

- 对端 SYN 的原始窗口直接使用；后续符合序号/确认校验的窗口更新才乘以对端 shift。
- 本地 SYN-ACK 最多通告 65535；已建立后满环可通告原始值 32768，实际窗口为 131072。
- 本地接收窗口按 shift 向下对齐。没有被通告的尾部字节不能接收；截取数据及 FIN 必须使用
  本次包进入处理时的窗口右边界，不能先建立连接再扩展同一个第三次握手包的合法范围。
- 旧重复数据、零窗口探测、部分 ACK、重传、半关闭、时间等待和既有规则/DNS/出站继续复用。
- 发送环及拥塞窗口仍受既有 32 KiB 限制；协商大对端窗口不会允许无界在途数据。

| 输入/状态 | 独立预期 |
| --- | --- |
| SYN：window=2000，WS=7 | 初始对端窗口仍是 2000 |
| 后续有效 ACK：window=3000 | 对端有效窗口 384000 |
| 本地协商后接收环空闲 | 128 KiB；ACK 中 window=32768，无 WS 选项 |
| 未协商 WS | 原 32 KiB 环及原始窗口，不伪造扩大 |
| SYN-ACK 已通告 65535，第三次握手 SEQ 在该范围外 | 不得因未来 128 KiB 窗口而接受该 ACK 完成握手 |
| 剩余容量 6 字节，本地 shift=2 | 只通告和接收其中 4 字节；剩余 2 字节不能越界使用 |
| WS=255、合法选项长度 | 按 14 使用，不产生溢出 |

## 内存与生命周期

未协商流仍预留 256 KiB；协商流预留 384 KiB。新增接收正文 96 KiB、位图 12 KiB，
增量在 128 KiB 预留中覆盖；双环、DNS 原响应/分帧、发送记录和临时正文沿用原预算说明。
全局 TCP 预算仍为 8 MiB；全为协商流时最多 21 条，未协商流最多 32 条，混合场景按实际租约准入。
默认每会话上限仍为 16。达到字节或数量上限明确返回资源错误，不改成直连或偷偷关闭协商。

内存租约在准备网络快照、连接和登记任务之前取得；准入失败不建立出站或留下 flow。
关闭完成后，即使外部保留 Session/owner，真实环缓冲及租约也已归还。
此预算不包括全部进程 RSS、系统 Socket 缓冲或线程栈，不能据此声称进程内存上限为 8 MiB。

未增加 YAML 字段或 C ABI 命令；协议选项在 Rust 内部处理。Swift 只传单个 IP 包和用户意图，
不读取缩放值决定规则、资源或连接状态。SACK 与扩大接收位图共用，协商选项共用有界 40 字节空间；未实现的时间戳、ECN、紧急数据及 TFO 不因本次协商而启用。

## L1–L4 独立核对与已知边界

L1：检查类型范围、32 位平台可表示的最大 65535<<14、缓冲边界及无 unsafe；编译和 lint 以实际命令为准。
L2：测试预期来自 RFC 7323 与上述独立数值，不从当前实现反推。
L3：SYN 不缩放、双方握手、接收窗口对齐与旧规则/生命周期分别核对；错误不部分提交、不降级 DIRECT。
L4：运行记录、同名报告与源码指纹分别保存，未验证平台不计通过。

开发时已观察到一项夹具错误：把带 MSS 的 SYN 直接改为 ACK 后，MSS 本身即非法，导致 WS 忽略测试提前失败。
现在用 NOP 替代该 MSS 字段，保留失败记录，不放宽生产 MSS 校验；WS=255、非 SYN 忽略和非法长度仍独立断言。
另在语义审查中补上第三次握手必须遵守已通告的 SYN 窗口，而非尚未发布的扩大窗口，并固定进入 process
时的接收右边界用于正文裁剪。

原始开发证据位于 `/private/tmp/fluxa-ws-*`。正式发布、App 固定二进制更新、macOS Network Extension、
最低系统/Intel、真实用户节点及长期高负载仍需各自验收；不能借本阶段合并 main 或从 dev 发布 crates.io。
