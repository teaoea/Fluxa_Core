# 内核本地验证与获准后的发布

源码统一使用 `main`；`-dev` 是开发二进制的预发布等级，不是分支。Nodus 源码已开源，后续二进制在同一个 `teaoea/Nodus-Core` 仓库分发。

当前不启用上传，不创建 Release、草稿或标签，永久禁止 crates.io。实际边界见 [发布与分发规范](../AGENTS/发布与分发规范.md)。

## 当前本地入口

1. 按 [测试迁移与执行说明](测试迁移与执行说明.md#本地质量检查与自动化边界) 完成适用的格式、Clippy、Rust、错误契约及报告检查，保留原始失败状态和未测项。
2. 只提交本次源码和适用文档到 main，禁止将代码审查报告提交或推送。
3. 获准构建时使用 `bash build-macos.sh --output <全新目录>/NodusCore.xcframework --package-dir <全新附件目录>`；当前只构建 macOS arm64。检查架构、部署版本、导出符号、真实宿主调用、来源与 SHA-256。
4. 默认仅保留本地产物；公开上传流程尚未重新启用，须等待单独授权和实际门禁验收。

## 历史手动发布步骤（已失效）

以下原步骤保留为历史，包含旧分支及分发门禁描述，不得直接执行。不能靠设置旧环境变量绕过当前上传关闭状态。

1. 完成格式、全目标 Clippy、Rust 测试、错误契约及真实 Swift FFI，保存原始退出状态、失败历史及未测边界。
2. 提交本次文件并推送 dev，在干净副本重跑检查。生成本机验证摘要，字段为 source_commit、fingerprint、checks 和 unverified。checks 必须逐项包含 format、clippy、rust_tests、error_contract、swift_ffi，均使用 status: PASS 与 exit_code: 0。未测项不能计通过。
3. 设置 NODUS_DEV_SOURCE 为完整提交、NODUS_DEV_REPOSITORY 为 teaoea/Nodus-Core、NODUS_DEV_VERIFICATION 为摘要文件，历史上运行 bash Tools/dev-release.sh --prepare <全新附件目录>。目录保留便于手动上传；不需要上传令牌。
4. 仅在用户明确授权上传后，才上传 provenance.json、nodus-core-macos-arm64.zip、nodus-core-fixture-macos-arm64.zip。公开清单记录 manual-local: 后跟本机摘要 SHA-256，不上传摘要原文或原始日志。
5. 在 Nodus-Core 选择 Draft a new release，标签为 v<版本>.<完整私有源码提交>。标签必须指向分发仓库自身的来源清单提交，不把私有源码推入公开仓库。
6. 保存草稿后重新下载三个附件，核对清单、SHA-256、源码提交、架构和包内容。通过后启用 Pre-release 并公开，不更新稳定 latest，不覆盖已发布版本。

可选本机命令 Tools/publish-core-binaries.py 支持现成的有限分发授权，执行相同草稿和下载核验。没有凭据则使用正常登录网页；不为发布创建或扩大访问权限。

本机手动附件入口单独构建 macOS ARM64，最低部署目标 13.0；其他受支持平台使用 [Apple 平台构建](Apple平台构建.md) 的本地多平台入口。最低系统运行、真实签名 App/Network Extension 和系统 VPN 的未验收边界必须保留。源代码、测试、构建脚本、用户配置和日志不得进入公开附件。永久禁止 crates.io。

未经用户明确许可不执行以上第 4–6 步；本地编译、校验并保存即为本地成品交付。
