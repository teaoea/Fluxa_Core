# Rust 网络代理内核统一错误代码体系设计、实现与审查

> **任务等级：MUST（强制执行）**
> **适用范围：** 当前 Rust 网络代理内核的全部模块
> **执行方式：** 实际检查源码、修改代码、补充测试、创建文档，并按《代码审查独立语义验证原则》进行独立审查
> **性质：** 实际代码改造任务，而非仅提供技术建议

**禁止为了统一错误代码而改变未经确认的内核业务语义。**

---

## 第一章：总体目标

建立统一、稳定、强类型、可扩展的 Rust 内核错误代码体系。

核心目标：

1. 所有对外公开的内核错误均具有明确的错误代码。
2. 每个错误代码具有唯一且稳定的业务语义。
3. 内核能够返回结构化错误信息。
4. 错误代码与自然语言错误描述分离。
5. 错误代码不依赖具体的错误字符串。
6. 错误传播过程中保留必要的诊断信息。
7. 不允许错误被静默吞没。
8. 不允许错误转换导致意外默认放行。
9. 不允许错误处理改变原有网络规则语义。
10. 不允许错误处理绕过认证、授权或资源限制。
11. 所有公开错误代码具有统一的权威定义。
12. 内核根目录必须创建完整的《错误代码查询表.md》。
13. 错误代码查询表必须与实际代码保持一致。
14. 必须建立自动化一致性检查。
15. 必须按照 L1、L2、L3、L4 完成审查。

**设计原则：** 错误代码用于机器识别；错误描述用于辅助诊断；错误上下文用于定位问题；错误处理后果由既定业务规范决定。不得混为一谈。

## 第二章：现有错误体系全面审查

修改代码之前，必须检查完整错误处理体系：

1. `Error` / `Result` 类型、错误枚举、错误结构体。
2. 错误创建、传播、`From` / `Into` / `map_err` 转换逻辑。
3. 错误序列化、API 错误响应、如存在的 IPC 错误响应。
4. 日志与诊断机制，以及实际使用的 `thiserror`、`anyhow` 等库。
5. 可能吞没错误、将错误转换为默认值或成功状态的代码路径。

必须覆盖实际存在的相关模块：配置管理、YAML/JSON 解析、配置验证、规则生成/编译/匹配、规则覆盖与裁剪、DNS、TCP、UDP、代理连接和转发、Debug Overlay、资源预算、内存分配、快照管理、并发状态、持久化、数据恢复、API 权限、生命周期管理等。

重点识别：

- 同一错误的多个标识；不同错误误用同一标识。
- 通过错误字符串判断类型；错误代码散落且互相冲突。
- 错误转换丢失真实原因、错误变成功、错误被忽略后继续执行。
- 异常情况下意外 `DIRECT` 或 `Continue`。
- 权限失败被混同为普通错误；资源预算错误被忽略。
- 非法配置部分接受；错误信息泄露敏感数据。
- 错误的实际处理后果与业务规范不一致。

**禁止未经审查就另建平行错误系统。**

## 第三章：错误代码设计规范

公开错误代码推荐大写英文单词与下划线组合，例如：

```text
CONFIG_YAML_SYNTAX_ERROR
CONFIG_YAML_UNKNOWN_FIELD
CONFIG_INVALID_RULE
CONFIG_UNSUPPORTED_VERSION
RULE_INVALID_TARGET
RULE_INVALID_MATCHER
RULE_RESOURCE_LIMIT
DEBUG_UNAUTHORIZED
DEBUG_SESSION_CLOSED
DEBUG_INVALID_LIFETIME
DNS_RESOLUTION_FAILED
NETWORK_CONNECT_TIMEOUT
NETWORK_CONNECT_REFUSED
NETWORK_UNREACHABLE
IPC_INVALID_REQUEST
IPC_PROTOCOL_MISMATCH
RESOURCE_LIMIT_EXCEEDED
INTERNAL_ERROR
```

**这些只是命名示例，绝不能未经检查就登记为已实现错误。** 实际代码必须来自真实存在的错误、已确认的业务规范和确实需要区分的失败场景。

公开错误代码必须：

1. 全局唯一，语义明确，长期稳定。
2. 不依赖自然语言，不含动态参数或敏感数据。
3. 不通过字符串拼接生成，不依赖枚举位置或魔法数字。
4. 不重复定义，不未经批准重命名，不复用废弃代码表达新错误。

必须区分内部错误类型与公开错误代码。允许多个底层错误映射至一个公开代码，但前提是具有已确认的语义归类关系，不掩盖不同的安全边界或处理后果，不丢失必要诊断，不影响既定恢复逻辑。**不能把各种不相关失败都归为 `INTERNAL_ERROR`。**

## 第四章：Rust 强类型错误定义

优先使用 Rust `enum` 表达公开错误代码，示意：

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash)]
pub enum ErrorCode {
    ConfigYamlSyntaxError,
    ConfigYamlUnknownField,
    ConfigInvalidRule,
    RuleResourceLimit,
    DebugUnauthorized,
    NetworkConnectTimeout,
    InternalError,
}
```

上述类型仅供设计参考，实际实现须适配当前工程。

要求：集中定义错误代码；提供稳定字符串表示；与错误文本解耦；尽可能采用穷尽式匹配；避免通配分支掩盖新增错误；不得通过枚举序号计算公开标识；不得让各模块随意手写未注册字符串。新增公开错误时必须触发一致性检查。

应优先扩展当前成熟的 `Error` 类型，不得为统一命名而无故重写。内部错误与公开错误允许采用不同的数据结构，但转换关系必须清晰、可验证。

## 第五章：统一结构化错误返回

在不破坏既有协议的前提下，公开 API 应返回稳定的结构化错误信息。推荐格式（仅为示例）：

```json
{
  "code": "CONFIG_YAML_UNKNOWN_FIELD",
  "params": { "field": "debug" },
  "trace_id": "7e9c2a41"
}
```

如项目已有 API/IPC 结构或不同序列化格式，应尽量复用，不得为了本任务擅自更换通信架构。

字段约束：

- **`code`：** 稳定错误标识；非自然语言；不包含动态值。
- **`params`：** 必要的结构化上下文，可包含 `field`、`rule_index`、`source_index`、`host`、`port`、`limit`、`actual`、`expected` 等；每个错误代码必须定义允许的字段名、类型、是否必填、含义、长度/数值范围、安全限制；禁止任意回传未经验证的对象。
- **`trace_id`：** 可选、仅用于关联受控诊断记录；不得直接使用指针地址或敏感内容。
- **`message`：** 如保留，仅作开发诊断，不能成为稳定的错误类型判断依据。

结构化错误不得改变原本 `Result` 的成功/失败语义；不能因序列化失败而把错误变成功；不能因参数生成失败触发越权默认行为。

## 第六章：错误代码与错误处理后果分离

每个公开错误代码都应有明确触发条件和经业务规范确认的处理后果。

示例（不得视为对现有代码行为的认定）：

- `CONFIG_INVALID_RULE`：规则校验失败；依照既定配置事务语义拒绝无效输入。若整体原子提交为已确认要求，则保持旧配置有效。
- `DEBUG_UNAUTHORIZED`：无权执行相应 Debug 操作；拒绝敏感修改。
- `RULE_RESOURCE_LIMIT`：操作超出预算；拒绝超限操作，不得绕过限制。
- `DNS_RESOLUTION_FAILED`：解析未获得合规结果；执行已确认的 DNS 失败策略，不能擅自默认 `DIRECT`。

**错误代码是故障表达，不是改变内核行为的理由。** 遇到规范不清的恢复/拒绝策略必须标记“待确认”，不能根据示例自行更改。

## 第七章：错误处理不得改变规则语义

本任务仅改造错误表示、分类与传播。不得无故改变 IP、DOMAIN、DOMAIN-SUFFIX、DOMAIN-KEYWORD、PORT/TRANSPORT、Local/Remote、REJECT、DNS 前后决策、Debug Overlay 的既定优先级和覆盖关系，不得更改规则去重、裁剪、匹配结果、出站策略选择。

严格区分：

- `DIRECT`：直连策略。
- `PROXY`：代理策略。
- `REJECT`：规则主动拒绝策略。
- `ERROR`：执行错误。

规则命中 `REJECT` 不是执行异常；远端 TCP 拒绝连接不是规则 `REJECT`；DNS 失败不是规则 `REJECT`。严禁“错误发生 → 错误被吞没 → 默认 `DIRECT`/`Continue`”。如发现原有这类问题，应记录为**独立业务缺陷**，不得在没有规范依据时擅自修改。

## 第八章：Debug Overlay 安全要求

既定安全契约：Debug 规则仅能通过**经认证与授权的本地 API** 创建和修改，不得进入配置文件、订阅、普通规则数据或持久化规则文件。

检查未授权调用、会话关闭、非法生命周期、资源超限、权限错误转换、Debug 状态部分更新、失败误报成功、错误回退、来源伪造等情形。

错误代码只表达实际失败，不能代替认证和授权。不得借错误代码改造增加权限入口或破坏 Debug 的隔离、优先级和临时生命周期。

## 第九章：错误信息安全要求

公开错误不得无条件包含密码、Token、私钥、代理认证信息、敏感配置原文、未授权文件内容、内存地址或不必要的内部路径。所有结构化参数必须有类型、长度和安全约束。

受控诊断系统应保存必要的底层错误链；公开错误应经安全筛选。不能把完整底层错误链直接公开，也不能以安全为名把一切错误粗暴归为 `INTERNAL_ERROR`。

## 第十章：内核根目录错误代码查询表（MUST）

必须先识别 Rust 网络内核真实根目录（Cargo Workspace 应确认内核 crate 的位置），然后在该根目录创建：

**`错误代码查询表.md`**

要求：UTF-8、标准 Markdown、中文说明、清晰分类、可搜索。必须完整收录所有**实际公开**的错误代码，不得遗漏、虚构或使用空泛解释。

该文档须能查询：代码含义、所属模块、触发条件、参数、真实处理后果、源码位置和兼容性约定，并支持独立代码审查。

## 第十一章：错误代码查询表结构

文档至少包含：

1. **错误代码体系说明：** 用途、命名、分类、稳定性、兼容性、内部/公开错误的区别。
2. **按实际实现分类：** 可使用 CONFIG、RULE、DEBUG、DNS、NETWORK、IPC、AUTH、RESOURCE、INTERNAL 等类别，但不得虚构分类。
3. **完整代码表：**

   | 错误代码 | 中文名称 | 所属模块 | 具体错误说明 | 触发条件 | 处理后果 | 错误参数 | 源码位置 |
   | -------- | -------- | -------- | ------------ | -------- | -------- | -------- | -------- |

4. **复杂错误专项说明：** 权限、预算、配置事务、DNS、规则匹配、内部状态、并发一致性等确实存在的错误。
5. **参数 Schema：** 名称、类型、必填性、语义、安全约束。
6. **兼容性约定：** 已发布代码不得改变含义或复用，新增登记，废弃标明状态。
7. **更新维护规则：** 每次新增、修改、废弃代码时同步更新文档和检查。

源码位置必须指向真实模块、文件、函数或其他可稳定定位的信息，**不得编造**。

## 第十二章：错误代码文档质量标准

不合格示例：

```text
CONFIG_INVALID_RULE：规则错误。
NETWORK_CONNECT_TIMEOUT：网络错误。
INTERNAL_ERROR：内部错误。
```

合格条目应说明真实失效条件和处置结果，如：

> `CONFIG_INVALID_RULE`：提交的规则类型、匹配值或策略参数违反内核校验规范。规则验证阶段发现不合法输入，导致该规则无法接受。内核应按已确认的提交语义拒绝该操作，不得静默丢弃错误后造成非预期放行。必须填写实际源码位置。

**以上仅为写作示例，并非已确认实现。** 无法查证的触发条件、语义或后果必须标记“尚未验证”，不能猜测。

## 第十三章：自动化文档一致性检查

必须建立自动检查，至少覆盖：

1. 公开错误全部登记、无重复、无虚构。
2. 代码名称、分类、参数 Schema 与文档一致。
3. 必要字段齐备：错误说明、触发条件、处理后果、源码位置。
4. 废弃标记正确；已发布错误代码的非法更改可被发现。
5. 新增错误而未同步文档时，检查应失败。

推荐使用 `error-codes.json` 或现有机器可读 Schema 作为单一权威定义，生成或验证 Rust 类型、结构化协议、参数 Schema、`错误代码查询表.md` 及其测试。可以选择自动生成或自动核验，但不得形成互不校验的多个权威定义。

**数量一致不意味着语义正确，仍须独立核实每一条映射。**

## 第十四章：资源预算与异常处理

检查错误对象无界增长、参数超长、错误链递归、日志放大、序列化不受控分配、格式化临时内存、绕过 ByteBudget、临时资源释放、旧快照滞留、生命周期问题。

重点覆盖内存不足、预算超限、整数溢出、长度超限、序列化失败、无效输入、锁状态异常、快照异常、文件损坏、恢复失败。不能因为生成丰富的错误上下文而额外引入资源耗尽风险。

## 第十五章：并发一致性

检查错误路径上的部分提交、锁释放、错误与快照版本对应关系、旧操作错误误归新版本、错误丢失或重复、竞态、死锁、资源无法回收、无效快照被继续使用等。

保持现有并发状态切换语义。发现既有并发缺陷时单独列出，**不得借本任务未经确认地重写并发架构。**

## 第十六章：兼容性约束

贯彻最小侵入原则。不得无故更改既定业务规范、分流逻辑、优先级、覆盖裁剪、DNS 决策、Debug 权限、资源预算、快照生命周期、配置格式、持久化格式、已发布 API、已发布错误代码和处理后果。

已公开错误代码不可静默重命名、复用或未经确认删除。必须发生不兼容变更时，列出修改原因、旧行为、新行为、影响范围、兼容策略、迁移和回滚方案。没有充分理由不得新增第三方依赖。

## 第十七章：Rust 测试要求

至少新增或完善：

**错误代码测试：** 唯一性、稳定性、类型映射、字符串表示、新增类型覆盖、已发布兼容性。

**序列化测试：** 正常错误、缺失/非法/超长参数、未知字段、长度超限、序列化失败。

**业务测试：** 非法配置、规则校验、DNS 失败、网络连接失败、Debug 非法操作、预算超限、状态异常、并发冲突。

**安全测试：** 敏感数据不泄露、权限/预算错误不变成功、失败不意外 `DIRECT` 或 `Continue`、校验不被绕过。

**回归测试：** 规则匹配、DNS 决策、Debug 优先级、资源预算、快照、配置事务语义不变。

**文档测试：** 公开代码齐全、无重复、无虚构、必填内容齐备、参数 Schema 一致。

禁止删除测试、弱化断言、修改已确认业务预期或跳过关键测试以获得通过状态。

## 第十八章：强制独立业务语义审查

执行《代码审查独立语义验证原则》（**MUST**）：

1. **技术验证不等于语义正确。** 编译、Clippy、单元/集成测试、参考实现或差分测试一致都不是充分证明。
2. **独立检查业务语义。** 核对规则优先级、覆盖关系、异常处理、安全边界、内存、并发、数据完整性、API 权限、错误代码真实性、实际处理后果。
3. **禁止循环论证。** 不得从生产实现反推预期；必须用独立确认的规范验证代码和测试。两个实现共同违背规范仍属缺陷。
4. **规范优先。** 代码/测试与规范冲突时调整代码/测试，不能篡改规范；规范不清须标记待确认。
5. **审查证据。** 重要问题必须记录规范、文件位置、实际/预期行为、最小复现、修复和回归测试。
6. **真实结论。** 明确区分“已确认正确”“已确认缺陷”“潜在风险”“尚未验证”；不能把静态推断冒充运行结果或把多个 AI 的相互引用当作独立证据。

## 第十九章：L1–L4 验收标准

- **L1 静态正确性：** 实际适用时运行 `cargo fmt --check`、`cargo check`、`cargo clippy` 和工程原有静态检查。
- **L2 实现一致性：** 运行 `cargo test`、相关集成测试、错误代码/文档一致性和兼容性测试。
- **L3 独立业务语义正确性：** 逐项验证错误映射真实性、分类、错误传播、处理后果、无意外放行、无权限/资源绕过、无来源伪造、快照一致性。
- **L4 审查证据核验：** 提供代码证据、真实测试结果、映射依据、修改记录、兼容性说明和尚未验证事项。

**L3 不得以 L1/L2 代替；L4 不得以主观判断代替证据。**

## 第二十章：实施流程

1. 检查项目结构，确认 Rust 网络内核根目录。
2. 全面审查当前错误类型、传播和公开路径。
3. 按真实错误和已确认规范设计统一代码体系。
4. 在现有 `Error` 体系基础上实施强类型改造。

## 后续明确修订：四位整数类别分段（MUST）

公开错误代码使用四位整数，不得以 0 开头。前两位表示错误类别，后两位表示该类别的具体错误。例如 `1001` 中 `10` 为类别、`01` 为具体错误，`1001–1099` 只能属于同一类别。原文中的字符串代码仅作语义命名示例，不作为公开 code 的表示形式。

类别号与具体错误号集中显式登记，不从枚举顺序或运行时算术推导；自动检查必须核验分段与语义类别一致。当前 `1001–1020` 混合多个类别，不符合新约定；实际改号前须制定已发布协议的兼容迁移方案，禁止静默改号、改义或复用旧号。各类别具体分配及尾号 `00` 的用途尚未确认。

## 后续明确修订：现有接口统一迁移（MUST）

用户已要求旧接口改为新方案。全部现有错误返回统一为分段四位整数及受限上下文，不维护旧错误双轨。已发布协议的变化必须报告并同步调用方；ABI 版本升级防止旧客户端误读，指针、预算、句柄及业务执行语义保持既定约定。
