# Nodus Core 内核开发约定

## 一、Core 范围与基础约束

- 本约定及本仓库专项规范仅记录 Core 的开发、接口、平台、安全、测试与交付约束；禁止混入其他产品的界面设计、适配实现、仓库安排、依赖接入或开发交付流程。外部边界只描述 Core 接受的输入、必须验证的授权、只读资源和对调用方提供的契约，不安排调用方内部实现。
- 本仓库维护 Rust 内核、C ABI、公开头文件、测试、示例及原生构建工具。Rust package 为 `Nodus-Core`，Rust／Clang 库名为 `nodus_core`，Apple 容器为 `NodusCore.xcframework`。
- 自研 Rust 网络处理，禁止引入 libXray、Xray-core 或 sing-box。公共协议、资源与生命周期按稳定职责复用，不复制网络流程或预建无实际用途的抽象。
- 必须完整阅读并遵循 [《内存与 FFI 安全规范》](内存与FFI安全规范.md)（MUST）。业务模块禁止 unsafe；仅必要 FFI／系统边界可局部使用，并以中文说明安全不变量，不持有跨语言业务裸指针。资源、任务、连接与缓冲区必须有上限。
- 配置采用 YAML；说明性注释、开发文档和提交信息使用中文，中英文 README 与默认模板按其约定语言维护。
- 自有代码采用 MIT，正文见根目录 `LICENSE`；第三方依赖来源、许可说明及原文见 `LICENSE.md` 与 `Notices/`，未完成审计不得宣称无许可风险。
- 按用户当前明确任务范围执行，不自行扩大功能范围；不删除或夹带其他任务的未提交工作，不提交 CA 私钥、节点凭据、流量导出、缓存或大型原生二进制。

## 二、只读输入、错误与生命周期

- 必须完整阅读并遵循 [《配置与资源文件所有权》](配置与资源文件所有权.md)（MUST）。Core 仅只读消费明确授权的配置和资源，不管理目录、创建／修改／修复／持久化文件或下载落盘；默认模板只提供纯内容。
- 必须完整阅读并遵循 [《错误代码体系设计》](错误代码体系设计.md) 全文（MUST）。现行公开错误协议由 `src/error.rs` 唯一定义，采用显式固定的四位整数（1000–9999）和 `CCEE` 分段，尾号 00 保留；不按枚举排列或运行时算术生成，不另建权威定义。各代码有中文注释，不静默改号、改义或复用已发布编号。
- 错误文档按下文 API 文档规则命名，记录真实源码、触发条件、处理后果及参数 Schema；变更同步协议、注释、示例和测试，并执行一致性及兼容性检查。当前 ABI、错误对象及调用接口使用同一权威错误协议，不并行维护未经授权的旧映射；新变更仍受兼容性授权约束，回滚必须匹配协议版本。
- 未完成能力明确拒绝；错误不得静默吞没、伪造成功、转成默认 DIRECT／Continue、混同策略 REJECT 与执行故障，或绕过授权和预算。错误改造不得擅改规则、DNS、网络及状态提交语义。
- 配置、订阅、IPC/API、Debug、DNS／网络、外部文件、缓存、恢复和 FFI／系统输入须逐项记录校验入口、信任依据、失败代码、状态后果及验证证据；不能以字段合法代替真实授权。
- 必须完整阅读并遵循 [《会话生命周期与资源所有权隔离原则》](会话生命周期与资源所有权隔离原则.md)（MUST）。Core 独立管理身份、Generation、租约、活动资源、取消与恢复；Arc／Weak 不是业务占用权。关闭主动撤销权限并等待必要释放完成，旧引用不得恢复活动权限，实际存活内存仍计预算；并发和重复关闭遵循专项契约。
- API 不得泄漏可变管理器、活动资源租约或内部决策控制权；平台结果经受约束接口验证，不能伪造系统接管成功。

## 三、规则、Debug 与 VPN

### 规则分类与优先级显式化

1. 核心匹配算法禁止使用没有明确语义的规则类别数字。
2. 所有规则类别必须具有唯一、明确、集中定义的名称。
3. 规则类别编号只用于内部索引，不代表实际匹配优先级。
4. 匹配优先级通过独立、明确的排序规则表达。
5. 禁止通过数字加减法推导不同来源的规则类别。
6. 修改类别定义必须检查索引生成、规则覆盖、候选选择、参考匹配及相关测试。
7. 首先保持现有行为；已确认的优先级业务错误按另行确认的规则规范修复。
8. 不为消除魔数引入不必要的动态分发、堆分配或其他运行时开销。
9. Debug Overlay 独立于正式规则类别，不能通过增加类别编号实现最高优先级。
10. 修改前后进行差分测试；预期业务语义变化另写明确预期的测试，不能只依赖两套实现自洽。

### Debug 专用本地 IPC（MUST）

必须完整阅读并遵循 [《Debug 本地 IPC 安全规范》](Debug本地IPC安全规范.md)。

Debug 仅使用独立本地 IPC，禁止 TCP／UDP Debug 监听及普通业务 API、配置、订阅注入控制命令。Core 验证 OS 对端身份、逐操作权限及全部字段／状态／预算；身份声明不是认证。Debug 仅存内存，TTL 必填且为 1–3600 秒，可在有效授权内优先于正式规则并覆盖 REJECT，但不能绕过安全边界。撤销、到期、关闭与有界审计由 Core 管理，禁止输出凭据或敏感配置。

### VPN 事务化启动（MUST）

必须完整阅读并遵循 [《VPN 启动技术规范》](VPN启动技术规范.md)。默认模式、必要检查、无节点风险授权、Preflight／Prepare／Commit／Verify、取消及失败回滚均按专项执行。未完成接管后真实验证不得标记 Running，失败不得自动切换其他模式或降级 DIRECT。

## 四、文档、示例与注释管理（MUST）

### 工作报告与提交审查（MUST）

- 每项独立工作区改动对应根目录一份 `工作报告-<任务名>.md`。编写或更新前必须完整阅读并遵循[《工作报告编写规范》](工作报告编写规范.md)，按任务复杂度说明范围、改动原因、已有验证、未解决问题及拟提交文件。
- 工作区提交审查必须完整阅读并遵循[《工作报告审查边界》](工作报告审查边界.md)，仅审查对应报告及其涉及的本次改动；该专项约束优先于一般性审查、测试及 L1–L4 要求，不据此扩展审查或重跑验证。
- 工作报告及其 `{工作报告名称}-修改意见.md` 仅保存在本地，不提交、不推送；对应改动获准提交时一并删除，不删除其他任务材料。提交与推送分别以用户授权为准。

### 文档归属与同步

1. **开发约束**统一保存在 `AGENTS/`，根目录 `AGENTS.md` 提供完整规范入口。
2. **代码文档**位于 `src/` 对应源码旁，与源码同名，例如 `src/ffi.rs` → `src/ffi.md`、`src/configuration/check.rs` → `src/configuration/check.md`，`mod.rs` 对应 `mod.md`。跨模块说明以真实流程负责人为主文档，其他位置链接引用。
3. **代码文档必须包含三项核心内容**，分别明确成节：**职责（干嘛的）**——实际负责什么、解决什么问题、输入输出及与其他模块的分工；**目标（想达成什么）**——期望达成的可观察行为、正确性／安全／资源目标，并区分设计目标、已实现能力与未验证部分；**禁止行为（不允许做什么）**——结合本模块明确禁止的副作用、越权、状态转换、数据访问、错误回退或资源操作，以及违反边界时的拒绝或失败后果。不能只写“遵守规范”代替具体禁止项。文档还须说明主要类型和入口、处理流程、调用关系、状态与资源生命周期、校验与错误、调用示例、对应测试及未实现／未验证边界；只列函数名或复述标题不算完成。
4. **API 文档（逐项完成）**：Core 每完成一项新增或修改的 API，必须同时编写或更新其 API 文档；文档缺失时该项不得视为完成。按真实调用边界分目录：`Documentation/API/External/` 保存外部调用 API（公开 Rust API、C ABI 及对外协议），`Documentation/API/Internal/` 保存 Core 内部自用 API（模块间入口与内部校验契约）。两类均使用 `{源码文件名}_api.md`，并按来源源码镜像子目录，例如 `External/configuration/check_api.md` 和 `Internal/vpn/platform_check_api.md`。同一源码同时包含两类接口时分别编写并相互链接，禁止以公开诊断类型掩盖内部授权入口。开头标明 API 分类、完整仓库相对源码路径、精确入口、调用对象和契约版本；说明输入输出、前提、权限／信任、错误、生命周期、副作用、示例、测试与未实现边界。私有辅助函数的实现细节仍归同名代码文档，不能把尚不可外部调用的入口宣传为外部能力。`Documentation/` 仅允许 API 文档、必要导航及机器契约，不混放模块说明、开发约束、性能报告、路线图或发布记录。同步入口、链接、生成器及测试，不保留两套权威契约。
5. **测试文档**放在 `tests/` 并与对应测试文件同名。测试目的、目标、判断标准、实际结果及性能测试方法／环境／版本／指标／证据／边界按测试专项编写。历史数据标明原版本及适用范围，不能冒充当前验收；报告更新保全需追溯的历史证据和手工说明。
6. **代码和测试注释**解释做什么、为什么、关键步骤、不变量与预期行为，安全边界说明前提；不固化性能实测耗时、吞吐、RSS 或通过结论。业务限额和判断阈值及其必要说明仍须保留，不能作为测量结果删除。
7. **项目介绍**为根目录 `README.md` 和 `README_ENGLISH.md`，互相链接，说明实际用途、能力边界、接入入口及许可证。
8. **示例同步**：配置或公开接口变化时，同步受影响的 `example_config.yaml`、`default_config.yaml`、`default_config_en.yaml`、其他完整示例、代码／API 文档及测试，并执行适用的严格解析或调用验证。中英文默认模板仅允许约定的语言差异，不得改变行为。新增或改变公开行为时提供可运行示例；纯内部变更维护受影响的既有示例、注释、文档及必要回归测试，不机械新增独立示例。README 随实际能力和公开使用边界变化更新。
9. **审查材料**不得提交或推送至 GitHub，包括审查报告、复核及结论汇总；已有未提交材料保留本地，不因整理、迁移或更名夹带提交。
10. **二进制同包交付**：每次打包必须把匹配版本的对外 API 文档、错误代码查询表及 JSON 与二进制放在同一 ZIP／交付包中；内部 API 不进入该文档目录。固定来源提交并核验清单，具体遵循《发布与分发规范》。
11. 文档迁移同步维护入口、源码引用、示例、生成器和工具的实际路径，保持公开 API、错误代码、安全边界和测试断言不变。

## 五、测试、兼容性与交付

- 必须完整阅读并遵循 [《测试文件与报告的管理》](测试文件与报告的管理.md)（MUST）。测试源码及同名文档集中于 `tests/`；注册、发现、隔离、独立预期、报告、历史保全及 L1–L4 按专项全文执行。结果真实可追溯，失败退出状态不得转成成功，未运行、忽略、局部执行及旧版本不得冒充通过。
- 必须完整阅读并遵循 [《API全生命周期管理》](API全生命周期管理.md)（MUST）。未正式发布的 API 可按约定调整并同步相关调用；已正式发布契约的兼容性、弃用迁移及不兼容修改授权继续有效，版本升级不能代替授权。
- 编译、格式、Clippy、单元／集成、参考／差分及文档一致不替代 L3 独立业务语义验证；L4 保留实际命令、结果、版本、映射及证据。数据包解析、回环诊断或发布不能代替真实系统 VPN、最低系统、真机或外部协议验收；条件不可用明确记为未测。
- 真实 ABI 验证固定受测源码提交、头文件、二进制及调用环境；验证语言不改变内核资源、安全、错误和关闭契约。

| 步骤 | 工作 | 完成标志 |
| --- | --- | --- |
| 1. 内核实现 | 实现任务范围内的 Rust API／C ABI 及相关说明和测试 | 独立程序可调用，能力边界明确 |
| 2. 内核验证 | 执行适用的 Rust、真实 ABI、协议互通与平台检查 | 实际结果、原始证据和未测边界可追溯 |
| 3. 源码交付 | 按授权范围提交、推送本次源码和可提交文档 | 来源明确，不夹带无关工作或禁止提交材料 |
| 4. 本地成品 | 任务要求构建时，从确定源码构建并校验 | 版本、源码、架构、ABI、最低系统及 SHA-256 对应 |

每项功能完成任务要求的适用流程后再进入下一项；源码交付和成品交付均不能冒充真实系统验收。

## 六、平台、分支与发布

- 必须完整阅读并遵循 [《全平台系统支持的最低版本》](全平台系统支持的最低版本.md)（MUST）。支持列表约束开发兼容性，构建列表约束实际执行范围；当前仅构建 macOS arm64，其他平台须明确指示后构建，不得因暂不构建而删去支持代码。最低版本、架构、排除平台和产物命名以专项矩阵为准。
- Core 仅在 main 开发、验证和交付源码，不创建 dev 或功能分支；开发版本、源码提交与正式发布状态分开。必须完整阅读并遵循 [《发布与分发规范》](发布与分发规范.md)（MUST）：永久禁止 crates.io；二进制及配套发布文件默认仅本地构建、打包、校验和保存。源码提交、推送、测试通过或功能交付均不构成二进制上传授权；未经明确许可不创建远程 Release、草稿或标签，不上传成品，也不启用关闭的上传入口。
