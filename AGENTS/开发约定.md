# Nodus Core 内核开发约定

- VPN 启动必须完整遵循 [《VPN 启动技术规范》](VPN启动技术规范.md)（MUST），包含默认 TUN 启用、其他模式默认关闭、Preflight/Prepare/Commit/Verify、必要前置检查、无节点本地二次确认、失败回滚及独立语义/信任边界验收。未经授权、检查和接管后验证不得标记 Running；失败不得自动切换其他模式或降级 DIRECT。该规范不代表现有系统 VPN 已完成。


- Rust package 命名 Nodus-Core，Rust/Clang 库名 nodus_core，网络引擎、C ABI、Swift FFI 门面与测试直接位于本仓库根目录；SwiftUI App 位于相邻 Fluxa 仓库，不复制到本仓库。
- 自研 Rust 实现网络处理，禁止引入 libXray、Xray-core 或 sing-box。交付 NodusCore.xcframework，内部库名始终 nodus_core；具体系统文件前后缀遵循全平台最低版本规范。
- 复用公共协议、资源和生命周期逻辑；业务模块禁止 unsafe。仅必要 FFI 边界可使用带中文安全说明的不安全操作，不持有跨语言业务裸指针；资源、任务、连接和缓冲区必须有上限。
- 配置采用 YAML。说明性注释、文档与提交信息使用中文；Swift 遵循 Apple API 设计、Google Swift Style Guide、SwiftLint 与 SwiftFormat。
- Core 统一在 main 实现、验证、提交和推送，不再保留 dev 或创建功能分支（2026-10-21 用户明确授权）。开发版本与正式发布状态分开管理；已正式发布的 API 不兼容变更、二进制上传仍须用户明确授权。测试通过不能代替发布或真实系统验收。
- 本仓库自有代码采用 MIT，声明保留在 ./LICESE.md；第三方依赖遵循上游协议，未完成审计不得宣称没有许可风险。
- 不提交 CA 私钥、节点凭据、流量导出、缓存或大型原生二进制。未完成能力明确拒绝，不伪造成功或回退直连。
- 功能顺序按用户最新指示：先补齐网络处理（规则、脚本管线、DNS、路由和出站基础），再做 TUN、网关，最后完善 SOCKS/HTTP 代理。macOS 优先，其他平台后续；编译、集成测试、最低系统、真机与审核分别记录。

- 永久禁止发布 crates.io。App 二进制接入遵循 Fluxa 仓库最新授权规范，生产构建不读取外部内核源码或构建 Rust。完整要求见 [发布与分发规范](发布与分发规范.md)，Nodus 内核源码已开源；后续二进制在同一 teaoea/Nodus-Core 仓库分发，本轮暂不启用上传。


- App 与内核编译产物默认仅在本地构建、打包、校验和保存；未经用户明确许可，禁止上传二进制及配套发布文件，也不创建远程发布草稿或发布标签。源码提交、推送和功能交付不构成上传授权；具体边界遵循 [《发布与分发规范》](发布与分发规范.md) 中“上传必须单独授权”。

- Apple 平台开发、依赖、构建与交付必须遵循 [《全平台系统支持的最低版本》（MUST）](全平台系统支持的最低版本.md)：macOS 13.0、iOS/iPadOS 16.0、tvOS 17.0；Mac 仅 Apple Silicon。不支持 Intel Mac、Mac Catalyst、watchOS 和 visionOS。

## 功能交付流程

| 步骤              | 工作                                                              | 完成标志                                                     |
| ----------------- | ----------------------------------------------------------------- | ------------------------------------------------------------ |
| 1. 内核功能开发   | 在内核 main 实现功能，提供 Rust API、C ABI 和 Swift 封装           | 独立测试程序可调用；未实现能力明确拒绝                       |
| 2. 内核验证       | Rust 测试、真实 Swift FFI、对应协议真实互通及目标平台检查         | 记录通过项与未测边界                                         |
| 3. 内核提交       | 功能及验证记录提交、推送 GitHub                                   | 确定发布源码提交                                             |
| 4. 内核版本发布   | 从确定源码在本地构建、验证并保存编译附件；上传须用户明确许可 | 编译附件、来源清单与 SHA-256 对应确定版本及源码 |
| 5. Fluxa 更新依赖 | 固定远程 Swift Package 版本并验证二进制 SHA-256                   | 使用已发布内核，无本地 Rust 构建或目录回退                   |
| 6. App 功能实现   | 接入新能力、UI、必要的 Apple 平台适配与错误展示                   | 用户能实际操作                                               |
| 7. App 验证与提交 | 旧功能回归、新功能运行及适用的真机行为检查，提交并推送 GitHub     | 验证边界明确，依赖版本可追溯                                 |

每项功能完成适用的本轮流程后再推进下一项；未获上传许可时，以本地构建和校验交付，不强制发布或推进依赖远程版本的步骤。目标平台、协议互通或真机条件不可用时记录未测，不伪造通过；发布不能代替功能验收，不得以提交 main 冒充正式发布或真实系统验收。

- 当前交付 TUN 数据包检查与有界 UDP 转发；DNS、路由和共用出站基础已完成。后续依次接入 TUN DNS、TCP 流和返回包、macOS Network Extension，之后网关、SOCKS/HTTP；UDP 回环测试不能代表系统隧道可用。每阶段分别验证及交付，不将数据包解析当成 VPN 已可用。

- 网络内核配置新增、修改或删除字段时，同步修改根目录完整示例 example_config.yaml（用户已合并替换旧示例），并执行解析验证；示例注释使用中文，README.md 同步说明实际能力与边界。

- 所有代码变更必须配套示例；修改代码时同步更新相关中文注释、文档和示例。配置字段变更同步所有完整示例并严格解析验证；示例明确可运行范围及未实现能力，不伪造成功。

## 规则分类与优先级显式化

1. 核心匹配算法禁止使用没有明确语义的规则类别数字。
2. 所有规则类别必须具有唯一、明确、集中定义的名称。
3. 规则类别编号只用于内部索引，不代表实际匹配优先级。
4. 匹配优先级通过独立、明确的排序规则表达。
5. 禁止通过数字加减法推导不同来源的规则类别。
6. 修改类别定义必须检查索引生成、规则覆盖、候选选择、参考匹配及相关测试。
7. 首先保持现有行为；已确认的优先级业务错误按另行确认的规则规范修复。
8. 不为消除魔数引入不必要的动态分发、堆分配或其他运行时开销。
9. Debug Overlay 独立于正式规则类别，不能通过增加类别编号实现最高优先级。
10. 修改前后进行差分测试；预期业务语义变化另写明确预期的测试，不能只依赖两套实现自洽。

## 统一错误代码体系（MUST）

- 全部 Rust 内核模块必须完整遵循 [《错误代码体系设计》](错误代码体系设计.md)（《Rust 网络代理内核统一错误代码体系设计、实现与审查》），约定等级为 **MUST（强制执行）**。该文件全部 23 章都是开发、审查与交付约束，不是建议或仅供参考的方案；开始相关工作前必须完整阅读，不得只读摘要或选取部分章节执行。
- 必须按该文件规定先审查真实源码及调用链，再实施错误分类、强类型定义、结构化返回、受约束上下文、传播、自动一致性检查、测试和 L1–L4 独立语义验收。代码、注释、示例与文档同步维护；未完成或无法确认的验收项标为尚未验证，禁止仅凭编译、测试、参考实现或文档一致宣布完成。
- 后续用户明确修订优先：公开错误代码使用显式固定的四位整数（1000–9999），不得以 0 开头，不使用字符串作为公开 code；集中重构现有 `src/error.rs`，不另建 `error_code.rs`；每个代码必须有中文注释；查询表及全部技术文档保存于 `Documentation/`，不放在根目录。上述修订只替换表示形式、定义位置和文档位置，不削弱原规范的语义分类、上下文、安全、兼容性及审查要求。
- 以《错误代码体系设计》全文及用户后续明确修订为准；摘要或整理稿不得替代全文或删减其要求。
- 四位公开错误代码按“前两位类别 + 后两位具体错误”分段：例如 1001 中 10 为类别、01 为具体错误，1001–1099 只能属于同一类别。类别号与具体错误号均须显式登记，不按枚举顺序或运行时数字运算推导；现有已发布编号与新分段冲突时必须先制定兼容迁移方案，禁止静默改号或改义。类别分配在真实源码核验后由唯一契约登记，尾号 00 当前保留不分配；不得虚构类别。
- 公开错误代码是内核协议；唯一权威定义为 `src/error.rs`，每个代码有中文注释，稳定含义与固定整数标识不依赖自然语言、枚举排列或读取方。
- `Documentation/错误代码查询表.md`必须记录真实源码、触发条件、后果及参数 Schema；任何新增、修改或废弃同步代码、协议、查询表、示例与测试，自动检查漏登、重复、虚构及未经批准的兼容性变更。
- 错误表示、诊断及执行后果分离；不得静默吞没失败、默认 DIRECT/Continue、混同策略 REJECT 与执行错误、绕过 Debug 授权或资源预算。既有业务语义不借错误改造擅改。
- 编译、Clippy、单元/集成、参考/差分与文档一致不能替代 L3；L4 必须有实际代码、运行结果、映射及兼容性证据，未确认项明确记录。

- 开发约束统一保存于 `AGENTS/`；代码技术文档、审查报告和错误查询表统一保存于 `Documentation/`，禁止放在根目录；README 保留入口，AGENTS 保留工具约束入口，许可证和构建配置保留必要位置。

- 各类外部输入必须遵循用户明确的输入验证矩阵（配置、远程订阅、IPC/API、Debug、DNS/网络、文件/缓存、持久化恢复、FFI/系统接口）；逐项记录校验入口、失败代码、状态后果与测试证据，未实现或未验证不得宣称通过。

- 用户已授权所有旧错误接口直接迁移到统一分段整数方案；禁止继续维护旧错误返回双轨。必须同步 ABI 版本、Rust/Swift 调用方、注释、示例、查询表及兼容性报告，明确回滚需要客户端与二进制整体还原。

## 会话生命周期与资源所有权隔离（MUST）

- 全部内核模块完整遵循 [《会话生命周期与资源所有权隔离原则》](会话生命周期与资源所有权隔离原则.md)，包括十三条强制原则、关闭与引用计数的区别、内核 BindingManager 绑定事务及 Rust/前端职责矩阵。
- 内核独立撤销会话身份、Generation 与资源租约，主动停止活动资源并等待必要释放完成；禁止使用 Arc/Weak 引用计数判断业务占用权。旧解析器/快照即使存活也不能阻止已释放资源重绑定，不能恢复被撤销的活动操作；实际保留内存仍计入预算。
- Closing 与 Closed 必须有真实完成边界；关闭、重复/并发关闭、启动中关闭、旧引用长期存活及获取/撤销竞态均需独立语义验证。内核负责完整生命周期与错误恢复，前端仅传递用户意图、展示内核权威结果及协调必要系统能力，不管理解析器、连接池、快照、租约、后台任务或内核运行逻辑。

## API 全生命周期管理与版本发布（MUST）

- 公开 API、配置和错误协议遵循 [《API全生命周期管理》](API全生命周期管理.md)。Core 2026-10-21 起只使用 main，不保留 dev；未正式发布的开发 API 可以同步调用方、注释、示例和测试后调整。
- 已正式发布 API 的兼容性、废弃迁移及不兼容变更授权仍有效。分支迁移不代表将开发版本宣布为稳定版，也不授权发布。
- SemVer、错误码权威定义、生命周期、信任边界、资源预算和 L1–L4 验证要求保持强制。永久禁止 crates.io；成品仅本地保存，上传须用户明确授权。
- API 不得泄漏可变管理器、活动资源租约或内部决策控制权；前端只传递意图和展示内核权威结果。

## Debug 专用本地 IPC 安全边界（MUST）

- Debug 控制仅使用独立本地 IPC，禁止开放 TCP/UDP Debug 监听；普通业务 API、配置、远程订阅不得注入 Debug 规则或绕过专用授权。
- Rust 必须验证操作系统 IPC 对端身份、具体操作权限，以及全部字段、状态和资源约束；客户端身份声明不是认证结果。
- Debug 仅存于内存，TTL 必填且 1–3600 秒；优先于正式规则并可覆盖规则 REJECT，但不能绕过认证、授权、协议校验、生命周期及资源预算。
- 状态、授权撤销、到期清理和资源关闭由 Rust 内核独立负责；记录必要授权与操作结果，禁止审计输出密钥、凭证或敏感配置。

## Swift 与 macOS 适配代码归属（MUST）

- 内核仓库仅保留 Rust 网络处理、C ABI、头文件及 Rust/原生二进制构建；禁止保存 Swift 源码（含 Package.swift、Swift 测试和封装）。
- Swift 数据模型、C ABI 调用封装及必要 macOS 系统能力协调统一位于 Fluxa 仓库 `Packages/FluxaKernelBridge/`；此规定取代将 Swift 封装/远程 Swift Package 放在内核仓库的旧描述。
- 适配直接作为 Fluxa 自身模块编译；内核二进制来源遵循 Fluxa 仓库最新授权规范并校验 SHA-256；禁止生产构建读取外部 Rust 源码或触发 Cargo。
- Rust 仍独立负责生命周期、资源租约、认证授权、网络决策与错误恢复；迁移 Swift 文件不向前端转移内核控制权。跨仓库源码 FFI 联调必须显式指定受测内核路径，不能作为生产依赖回退。

- 系统支持列表与构建列表分开遵守：开发保持全部约定平台兼容，当前默认仅构建 macOS arm64；其他平台等用户开发对应 App 并明确指示后构建。不得以暂不构建为由删去支持代码或依赖约束。
