# 《API全生命周期管理》

> **规范等级：MUST（强制）**
> **适用对象：Rust 网络内核；其 Rust 公开 API、原生构建产物及对外承诺的配置/错误协议等契约**
> **管理目标：main 中尚未正式发布的契约允许演进，正式发布保持可预期兼容；废弃 API 有警告、有迁移期、有授权移除机制；永久禁止 crates.io；内核源码开源，后续成品在同仓库分发且须明确授权。**

## 1. 规范目的与基本立场

1. **稳定不等于永久保留。** 已发布 API 的使用者有合理的迁移预期，但项目不得因过时接口而无限堆积兼容层。
2. **开发不等于免于正确性约束。** main 中尚未正式发布的 API 可按约定调整，但业务语义、安全边界、信任边界和资源生命周期要求始终生效。
3. **发布权与开发权隔离。** 所有执行环境永久禁止发布 crates.io；稳定二进制仍须审核、来源可验证的 `main` 提交及相应发布授权。
4. **不兼容操作必须经授权。** 对 `main` 已发布公开 API 的不兼容变更，包括计划中的移除，未经用户明确授权一律禁止。
5. **内核自主。** API 不得把规则、会话、资源管理、VPN/TUN 接管和内部状态决策权交给外部调用方；受控命令是请求而不是直接控制权。
6. **审查独立。** 编译通过、单元测试通过、API 对比工具未报警，均不能替代独立业务语义和安全验证。

本规范中的“必须/MUST”“禁止/MUST NOT”具有强制约束；“应当/SHOULD”允许有记录的例外；“可以/MAY”是可选做法。凡本规范与其他安全、业务约束同时适用时，**不得以版本兼容或便利性为由降低安全要求**；如出现冲突，应提交明确的设计决策和授权请求。

## 2. 范围与定义

### 2.1 API 范围

本规范覆盖：

- Rust crate 对外可使用的公共函数、方法、结构体、枚举、trait、关联项、泛型边界、公开模块和重导出。
- 对外承诺的 Cargo Features、支持的平台/最低 Rust 版本（MSRV，若项目已作承诺）、以及会改变消费者编译或行为的依赖契约。
- 由 Rust 内核提供的公开命令、只读状态查询及协议结构。
- 已对外承诺稳定的配置格式、错误协议、统一错误代码含义、业务语义。
- 内核构建产物、版本、标签、获准后的发布流程和迁移文档。

不因出现 `pub` 就自动认定 API 已经稳定：需结合**实际可达性、发布记录和公开承诺**判定；相反，公开行为即使函数签名不变也可能构成不兼容变更。

### 2.2 关键定义

| 概念             | 定义                                                                                               |
| ---------------- | -------------------------------------------------------------------------------------------------- |
| 未发布 API       | 尚未包含在任何正式发布的 `main` 版本中的接口，可调整而不承担对外历史兼容义务                       |
| 已发布稳定 API   | 已经通过经审核的 `main` 正式版本对外发布，并纳入稳定契约的接口                                     |
| Deprecated       | 仍可使用但明确宣布将淘汰的已发布 API；正常编译时应可发出弃用诊断                                   |
| Migration Window | 为使用者提供替代接口、迁移文档及足够时间的过渡期                                                   |
| Removed          | 在经授权的不兼容版本中正式删除；不能再通过原接口访问                                               |
| 不兼容变更       | 可造成已有受支持调用不能编译、协议无法处理、或既定公开行为发生破坏性改变的修改                     |
| 授权             | 用户对具体不兼容变更、影响范围、目标版本及迁移安排作出的明确批准；不得由 AI、CI 或期限届满自行推定 |

## 3. 单一 main 分支（MUST）

Core 仅使用 main 开发与提交；不创建 dev 或功能分支，不移动历史标签、不重写已发布版本。

1. 未正式发布的开发 API 可直接改造，同步调用方、注释、文档、示例和测试；不为未承诺的旧入口增加兼容债务。
2. 已正式发布 API 继续受到兼容性、废弃迁移和用户明确授权保护，不能因同在 main 而擅自破坏。
3. main 提交、测试通过和预发布版本号均不构成正式发布或二进制上传授权；默认只交付本地产物，永久禁止 crates.io。

## 4. 语义化版本与契约版本

### 4.1 内核版本：SemVer

使用 `MAJOR.MINOR.PATCH`：

- **PATCH**：向后兼容的缺陷修复与内部优化。
- **MINOR**：向后兼容的新公开能力。
- **MAJOR**：经明确授权后引入破坏性公开变更的正式发布。

SemVer 的 `0.y.z` 按标准不承诺稳定 API；**但项目对 `main` 已发布 API 的“未经授权不得破坏”规则仍然适用**，不能以 `0.x` 为借口绕开批准。

版本号不能代替授权；仅提高 MAJOR 并不能自动允许移除 API。修复漏洞导致的不兼容变更，仍须走本规范的安全紧急变更机制。

### 4.2 独立版本不得混用

内核 SemVer、配置格式版本、公开错误协议版本，以及 GeoIP 等外部数据版本，按各自契约独立维护。**不得把外部数据库的版本绑定为内核版本。**

统一错误代码采用项目已有的**四位十进制 `CCEE`（两位类别、两位具体错误）**规则。已发布错误代码必须保持含义稳定，不得回收重用。涉及新增、废弃或修改错误时，更新 `Documentation/API/error_api.md`，保留引入版本、状态、触发条件与真实处理后果。

本规范**不预先分配任何具体错误码**；错误码只能从权威登记表分配并通过冲突校验。

## 5. API 生命周期状态机

每个已发布公开 API 遵循：

```text
Active
  │ 决定淘汰、确定替代方案和迁移计划
  ▼
Deprecated（仍正常工作，发出编译期弃用警告）
  │ 迁移期：文档、示例、版本提示、兼容性维护
  ▼
EligibleForRemoval（达到时间/版本条件，仅表示具备申请资格）
  │ 具体破坏性变更获得用户明确授权
  ▼
Removed（在获授权的正式不兼容版本中删除）
```

1. `Deprecated` 不是 `Broken`：过渡期内不得仅因废弃而让旧 API 返回失败、改变原有语义或抛出恐吓性的运行错误。
2. 达到淘汰期限**不等于自动获得删除权限**。
3. 已确认为危险且无法安全维持的 API，可启动安全紧急变更程序；不得假借普通兼容性要求长期保留已知高危行为。
4. 不得让 API 无计划地长期停留在 Deprecated；保留例外须有理由、负责人、下一次复审时间和退出条件。
5. 未正式发布的开发 API 不强制进入上述迁移状态机，可以直接删除。

## 6. 弃用诊断：调用旧 API 必须触发警告

### 6.1 编译期警告（MUST）

正式废弃的公开 Rust API 必须使用 Rust 标准 `#[deprecated]`，并给出**正式废弃版本、替代 API、迁移文档指引**。例如，以下示例仅演示一个**只读、无管理权限**的版本查询接口，不对应现有项目的真实 API：

```rust
/// 读取内核公开支持的配置格式版本；不修改内核运行状态。
pub const fn supported_config_schema_version() -> u32 {
    1
}

#[deprecated(
    since = "1.4.0",
    note = "改用 supported_config_schema_version()；迁移说明见 API_DEPRECATIONS.md"
)]
pub const fn legacy_config_schema_version() -> u32 {
    supported_config_schema_version()
}
```

调用已废弃函数时，**在未抑制 `deprecated` lint 的正常编译环境中**，编译器应给出弃用警告。不能声称 Rust 能强制所有依赖方显示警告：下游代码可能使用 `#[allow(deprecated)]` 等方式抑制诊断。

**禁止**用 `#[deprecated]` 作为破坏兼容的借口，也不得在弃用消息中承诺未经授权或未经批准的具体删除版本。

### 6.2 运行时诊断（按需）

- 常规 Rust API 优先使用**编译期弃用警告**；**不要求**每次调用时记录运行时 WARN。
- TCP/UDP/DNS、规则匹配等高频路径，不得按调用次数无限输出废弃警告。
- 确有运行期诊断需要时，应制定按作用域限频/首次告警机制，并遵守日志隐私和资源预算限制。
- 不能因为接口进入 Deprecated 阶段就将正常调用转换为 ERROR。

### 6.3 内部自用约束

- 新内核代码 **MUST NOT** 再调用 Deprecated API。
- 应优先把内部调用迁移至新接口；旧入口只作为对外过渡适配层。
- 本地检查必须检测内核自身使用 Deprecated API 的行为；未来启用 CI 时执行同等级检测；可在适当 crate/模块启用 `#![deny(deprecated)]`，但若存在例外，必须精准限定位置、注明原因和到期条件。
- **不得要求所有下游用户将警告升级为编译错误**。

## 7. 默认迁移窗口

### 7.1 双条件

已发布稳定 API 的普通淘汰流程，默认须同时满足：

1. **至少 6 个自然月**：从正式版本首次公布废弃通知之日开始计算。
2. **至少跨越 2 个后续正式 MINOR 发布版本**：开发者应实际获得两个可迁移的正式次版本机会。

例如，API 在 `1.3.0` 首次废弃：原则上先经历 `1.4.0` 和 `1.5.0` 两个后续正式 MINOR，且距 `1.3.0` 发布已满 6 个自然月，才具备申请在后续 MAJOR 删除的资格。**这些版本仅为示例，不表示实际发布计划。**

若发布节奏、生态影响或迁移难度较大，应延长迁移期。禁止通过一次性快速发布空 MINOR 版本机械凑数规避“充分迁移”的本意。

### 7.2 迁移准备

正式宣告 Deprecated 前应准备：

- 能实现原有合法业务意图的替代接口，或说明为什么某功能应当彻底撤销。
- 从旧 API 到新 API 的迁移指引，标注语义差异、权限要求及行为差异。
- 如存在破坏性数据、配置或错误契约变更，应给出迁移与回滚方案。
- 对预期受影响的调用方式给出不含敏感信息的示例与验证方法。

### 7.3 充分过渡的边界

迁移期间，除经授权的安全例外外，旧 API 必须继续履行已承诺的有效行为。不能通过减少能力、故意增加严重性能损耗、静默改返回值等方式逼迫迁移。

## 8. 删除授权与紧急例外

### 8.1 普通删除审批（MUST）

拟移除已发布稳定 API 时，必须事先给出：

1. API 完整标识及首次正式发布版本。
2. 废弃时间、过渡版本、迁移期实际经过情况。
3. 删除原因：冗余、替代、错误设计、维护成本或其他可核验原因。
4. 受影响的编译调用、配置/协议、运行行为和依赖方。
5. 推荐替代方案与迁移样例。
6. 对规则优先级、失败处理、权限、资源所有权与并发语义的独立评估。
7. 目标正式版本、发布说明和回滚/补救方案。
8. **用户对本次具体不兼容变更的明确授权记录。**

禁止把“已达到移除日期”“构建成功”“CI 通过”或“计划中已列出”视为授权。

### 8.2 安全紧急例外

发现已发布 API 存在严重安全风险且无法在原契约内安全修复时：

- 优先评估最小范围的安全修复、特性禁用或受控缓解措施。
- 提交漏洞原因、影响面、继续保留风险、替代路径和建议发布时间。
- 按项目授权要求取得明确决定，再实施必要的不兼容措施。
- 在技术上不可避免的系统级应急阻断，应如实记录状态和实际影响，不得假装旧契约仍被满足。

紧急例外不能被当成常规清理接口的捷径。

## 9. 禁止兼容性债务无限增长

### 9.1 禁止事项

- 为 未发布开发历史版本保留没有外部承诺的旧入口。
- 同一业务语义长期并存多个 `_v2`、`_v3`、`_legacy`、`_compat` 包装，而无明确必要性。
- 仅为避免修改内核内部调用而增加适配层。
- 已废弃 API 的内部依赖持续增加。
- 删除旧 API 后换名重新引入原有设计缺陷。
- 利用公开兼容包装绕开授权检查、资源租约、会话状态机或输入校验。

### 9.2 有理由的临时兼容

保留已发布稳定 API 的迁移期包装可以是必要的，但必须：

- 记录它对应的已发布契约。
- 保持旧 API 已承诺的合法语义。
- 不复制两套可漂移的业务实现；优先向同一经过验证的内部实现收敛。
- 不延长旧活动资源的使用权，不直接暴露管理器或内部快照所有权。
- 明确删除条件、目标版本和复审日期。

**不得为维护旧 API 而保留危险的资源所有权结构。** 若原 API 直接泄漏内部活动资源所有权，应提出适当的安全迁移与授权方案。

## 10. 定期盘点与治理节奏

1. **至少每 3 个月**执行一次公开 API 盘点。
2. 每次正式发布前必须审查新增、变更、废弃、待移除 API。
3. 重点识别：没有真实外部使用价值的接口、重复功能、多代包装、无限延长的弃用、错误的权限暴露、非必要公开类型、旧版本兼容分支。
4. 每个 Deprecated API 必须记录最近一次复审日期、当前迁移阻碍与下次复审安排。
5. 盘点形成明确结论：保留并说明原因、启动废弃、延长迁移期限、申请授权删除、或拒绝新增公开接口。
6. 盘点不得自动触发对 `main` 已发布 API 的删除；删除仍受第 8 章约束。

## 11. API 废弃登记表

Rust 内核仓库应维护 `API_DEPRECATIONS.md`，至少记录：

| 字段               | 要求                                               |
| ------------------ | -------------------------------------------------- |
| API 标识           | 精确至 crate、模块、类型和项                       |
| 引入版本           | 最早正式公开版本；无法确认须标注待核实             |
| 废弃版本及发布日期 | 用于计算真实迁移期                                 |
| 原契约             | 原有调用方式及对外行为                             |
| 废弃原因           | 可核验的技术或业务原因                             |
| 替代方案           | 新 API 或明确的停止使用方案                        |
| 迁移说明           | 调用差异、示例、风险、验证方法                     |
| 下游影响           | 来源于检查或证据，不得臆造                         |
| 最早移除资格       | 同时满足 6 个月与 2 个后续 MINOR 的日期/版本条件   |
| 计划移除版本       | 未批准时标明“待授权”，不得伪造承诺                 |
| 用户授权           | 授权范围、日期与对应变更记录                       |
| 当前状态           | Active / Deprecated / EligibleForRemoval / Removed |
| 审查信息           | 责任人、最近审查、下一审查                         |

**登记示例（虚构，不对应真实接口）：**

| API                              | 废弃版本 | 替代方案                            | 最早移除条件                         | 移除授权 |
| -------------------------------- | -------- | ----------------------------------- | ------------------------------------ | -------- |
| `legacy_config_schema_version()` | `1.3.0`  | `supported_config_schema_version()` | 满 6 个月且已经发布 `1.4.0`、`1.5.0` | 待授权   |

对于统一错误代码，应保持其单独权威登记表，不得仅通过删除 Rust API 就回收旧错误码编号。

## 12. 开源源码与分发边界

1. Nodus 内核源码已开源，唯一仓库为 `teaoea/Nodus-Core`；自有代码 MIT，保留第三方声明。
2. 获准后的二进制分发也使用该仓库；未经新的明确授权，上传入口保持关闭，不创建远程 Release、草稿或标签。
3. 永久禁止 crates.io；内核开源及源码提交不构成二进制上传授权。
4. 版本、API 兼容性、安全、验证及逐次上传授权继续遵循《发布与分发规范》。历史记录不重写。

## 13. 本地质量检查与自动化边界

当前由本地执行器和人工检查完成下列要求，结合独立业务语义验证形成证据。当前不启用 GitHub Actions，也不假定存在自动 pre-push 或服务器端门禁；未来启用 CI 时必须执行至少同等级检查。未实际执行的检查必须明确标记为未验证：

| 检查                                       | 目标                               | 不能证明什么                         |
| ------------------------------------------ | ---------------------------------- | ------------------------------------ |
| Rust 构建及测试                            | 基础实现可用性                     | 不能证明业务规则正确                 |
| API diff / `cargo-semver-checks`（如适用） | 发现公开 Rust API 层面的破坏性变化 | 不能覆盖所有行为兼容性或所有目标平台 |
| `#[deprecated]` 诊断测试                   | 证实正常调用旧 API 产生警告        | 不能阻止下游主动抑制 lint            |
| 内核自身 deprecated lint                   | 避免内部新增旧接口依赖             | 不能替代公开 API 盘点                |
| 契约测试                                   | 比较配置/错误协议与承诺行为        | 不能证明未覆盖边界条件正确           |
| 发布守卫                                   | 限制发布来源与包内容               | 不能代替权限管理和审核               |
| 文档一致性校验                             | 确保废弃登记、版本与代码一致       | 不能自动证明迁移方案充分             |

涉及正式 API 的 PR 必须提供：

- 相对上一正式发布基线的变更列表。
- 分类：兼容新增、兼容修复、不兼容候选、废弃声明、正式移除。
- 已发布契约影响及独立业务语义分析。
- 如有不兼容变更，附用户明确授权；没有授权则不得合入 `main`。
- 对统一错误码和配置协议的影响报告。
- 实际执行的检查命令与结果；未执行的应明确标记为“未验证”。

## 14. 必须独立验证的内核业务不变量

即使变更仅为 API 改名或兼容层清理，审查也必须独立核对：

1. **规则语义：** 优先级、覆盖、剪枝及 Debug 规则的权限约束未被错误改变。
2. **故障语义：** 不得吞错、静默降级或在代理故障时擅自放行 DIRECT。
3. **信任边界：** 配置、订阅、API/IPC、DNS/网络数据、缓存、外部文件与跨模块传递均应执行实际必要的校验与授权。
4. **生命周期：** 会话启动、关闭、取消、热更新与恢复均由内核掌控；外部持有旧句柄/旧快照不得延长已撤销的活动资源租约。
5. **资源预算：** 旧引用实际占用的内存仍计入预算；释放租约不意味着对象内存立即回收。
6. **并发原子性：** 旧会话不得在关闭竞态中重新申请已撤销资源；配置和快照更新不能出现部分提交。
7. **接管安全：** VPN/TUN 仅在规定的前置检查和授权通过后进行接管；接管后需要验证真实数据路径，不能仅凭进程存活判定成功。
8. **GeoIP 约定：** 没有 `geoip_url` 时为合法禁用并记录 WARN；显式配置后初始化失败应为 ERROR，不能回退至内置默认 URL 或数据库。
9. **系统边界：** macOS 系统接口仅执行经授权的必要系统操作并报告真实结果；内核不得把业务逻辑控制权外包。
10. **错误代码：** 错误含义不得重用，所有公开错误均须在权威表中可追溯。

上述各项应采用独立需求作基准核对，而不能以旧代码、旧测试或 AI 自己生成的参考实现作为唯一权威。

## 15. L1–L4 独立审查与缺陷报告

- **L1 静态正确性：** Rust 类型、可见性、借用/所有权、公开签名、编译及 lint。
- **L2 实现/测试一致性：** 测试覆盖实际修改且断言与预期契约一致，不能直接从实现反推期望。
- **L3 独立业务语义：** 对规则优先级、覆盖关系、异常处理、安全边界、生命周期和授权逐项核对。
- **L4 证据核验：** 记录实际运行的命令、测试、差异与发布包检查；未验证不得标注已验证。

发现问题时须至少说明：

1. 违反的业务/兼容契约。
2. 真实代码位置、受影响版本和 API。
3. 实际行为与应有行为。
4. 最小可复现路径和影响范围。
5. 建议最小修复方案及回归验证。
6. 结果分类：已确认缺陷／潜在风险／尚未验证／已确认正确。

## 16. 示例：正确与错误的 API 淘汰方式

### 16.1 正确：只读 API 迁移

```rust
// 仅用于演示，不属于项目现有 API 登记。
pub const fn supported_config_schema_version() -> u32 {
    1
}

#[deprecated(
    since = "1.4.0",
    note = "使用 supported_config_schema_version()；详见 API_DEPRECATIONS.md"
)]
pub const fn legacy_config_schema_version() -> u32 {
    supported_config_schema_version()
}
```

符合要求之处：调用方会收到正常的编译期弃用警告；旧接口在过渡期保留既定结果；新接口仅提供查询，不泄露内核资源管理权；移除必须另行申请授权。

### 16.2 错误：不必要的多代兼容入口

```rust
// 反例：不应无期限增加名称不同、语义相同的公开包装。
pub fn status_v1(&self) -> KernelStatus { /* ... */ }
pub fn status_v2(&self) -> KernelStatus { /* ... */ }
pub fn status_v3(&self) -> KernelStatus { /* ... */ }
```

若 `v1/v2` 已正式发布，应进入明确废弃与迁移流程；若属于 main 中尚未正式发布的 API，可以直接清理，不必产生新的兼容负担。

### 16.3 错误：对外暴露内核资源控制权

```rust
// 反例：不应向外部暴露可操作的内部资源管理器。
pub fn binding_manager_mut(&mut self) -> &mut BindingManager {
    /* ... */
}
```

应使用内核拥有完整权限检查和状态机校验的受控请求接口；外部调用方不应直接获得活动绑定、解析器、快照或资源租约的控制权。

### 16.4 错误：把废弃变成运行故障

```rust
// 反例：仅因 deprecated 就让原本合法调用失败。
#[deprecated(note = "已废弃")]
pub fn legacy_query(&self) -> Result<QueryResult, KernelError> {
    Err(KernelError::DeprecatedApi) // 禁止仅凭废弃状态制造失败
}
```

该片段为**反例伪代码**，其中错误类型及变体并非真实项目定义；不得据此新增未经登记的统一错误代码。

## 17. 正式发布验收清单

发布前每项均应有实际结果或证据；不满足时不得声明符合规范：

- [ ] 发布代码来自已审核、受保护的 `main` 提交。
- [ ] 版本 Tag 来源、提交、Cargo 版本、包内容一致。
- [ ] 发布凭据不对普通 PR 或未授权流程开放。
- [ ] 已与**上一正式发布版本**比较 API，记录全部不兼容候选。
- [ ] 已发布 API 无未经用户授权的破坏性修改。
- [ ] 新公开 API 有必要性审查，未额外暴露内部内核管理权。
- [ ] Deprecated API 已标注 `#[deprecated]` 且可产生正常编译期警告。
- [ ] 已提供替代方案、迁移文档、废弃登记及下次复审计划。
- [ ] 待删除 API 满足默认迁移窗口，且移除获明确授权。
- [ ] 旧错误代码未被重用；统一错误代码查询表已同步。
- [ ] 配置/错误协议版本与契约变化相符。
- [ ] 已完成独立业务语义、权限、生命周期、资源预算及并发审查。
- [ ] 已检查实际内核成品内容、公开头文件、依赖／Features、平台／架构／ABI、来源及校验值，并记录实际检查结果。
- [ ] 本地质量检查与实际执行证据一致；未来 CI 的结果同样可追溯，未执行的验证未被伪称已完成。

## 18. 冲突处理与执行优先级

当不同目标发生冲突时，按以下规则处理：

1. **安全与业务语义正确性不可为了 API 兼容而静默牺牲。**
2. 已发布 API 的不兼容修复、替换或删除须按明确授权机制处理。
3. 已发布 API 未经授权不得破坏；已废弃不等于已授权删除。
4. 对 main 中尚未正式发布的 API，优先采用精简、正确、可维护的设计，不承担无必要的历史兼容成本。
5. 永久禁止所有 crates.io 发布；获准后的二进制仅在 `teaoea/Nodus-Core` 同仓分发。
6. AI 不得以自认为架构更好、测试通过或期限已到为由代替用户作出不兼容变更授权。

## 19. 最终强制约定

**Core 统一 main；未正式发布的开发 API 可重构，已正式发布契约仍受保护。业务、安全和内核自主约束绝不放松。**

**`main`：保护已经正式发布的公开契约；未经用户明确授权，不得不兼容修改。**

**Deprecated：旧 API 可继续调用，但正常编译应产生明确的弃用警告，并有替代方案与迁移文档。**

**迁移期：默认至少 6 个自然月，且经历至少 2 个后续正式 MINOR；届满只表示可申请删除，不表示自动授权。**

**淘汰：至少每 3 个月盘点无必要的公开 API；禁止无限期堆积多代兼容层。**

**发布边界：任何环境均永久禁止 crates.io；源码与获准后的成品同仓维护，默认只保存本地产物，上传须明确授权。**

**审查：坚持 L1–L4 独立验证；对规则语义、异常处理、安全边界、内核生命周期与资源所有权进行逐项核对。**
